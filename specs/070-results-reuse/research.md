# Results, reuse and completion research

## Decision

Store Results as Tier 1 records in the clean library catalog, `crates/persistence/library`, through its single serialized writer. A Result is a file that a View's processing wrote into the View's recorded output location, or a file the user attached to a View. Discovery reads the output location, lists candidates apart from intermediates that the View's profile recognizes, and labels files still being written Pending. Acceptance binds the user's choice to freshly hashed bytes and changes no lineage. Accepted products become product inputs of another View only after their bytes match the acceptance digest again. Mark Complete is a separate append-only decision. The plan reuses no legacy artifact table, watcher, classifier or command.

## Source evidence

## Cross-spec seams

Siblings 066 to 072 are planned in parallel, so their contracts were not available. Each seam states the interface RES needs and the conservative default that applies when the sibling contract differs.

- **CS1 VSEL View record.** RES reads the View ID, name, optional Project ID, optional originating Target ID, current membership revision and current member sessions. It creates a View with no sessions and an optional Project. It creates the next membership revision with unchanged sessions when product inputs change. Both writes must be callable inside RES's writer transaction. Default: when VSEL exposes only public async methods, the RES integration owner extracts their transaction bodies into crate-private functions in VSEL's module and changes no behavior.
- **CS2 Revision guard.** D09 requires Reopen before a new membership or preparation revision of a Complete View. RES owns the completion record and a crate-private `require_view_open(conn, view_id)` check. The 069 contract names the hook for it in PREP's preparation-start and Retry transactions; no View is Complete before 070 lands, and the RES integration owner adds the call there. Default for VSEL: the RES integration owner inserts the call into VSEL's membership-revision write. VSEL notes, RES attach and acceptance, LIB remap, and STO cleanup and reference repair never call it.
- **CS3 Output location.** PREP records the output location per preparation revision (PREP-FR-07): native path and folder identity, `<View>/output/` by default, or `<override>/<View folder name>/`. RES reads it, and the profile of that revision, through `Catalog::latest_preparation(view_id)`. Default: a View without a recorded output location lists only its attached files and reports `outputLocation: null`.
- **CS4 Profile capability.** PREP-FR-01 requires product-input and recognized-output evidence before a verified-profile claim. The 069 planner confirmed that the profile manifest has the capability classes `productInput` and `recognizedOutput`, both unknown by default. RES needs, per profile, the supported product-input kinds, whether mixed raw and product inputs are supported, and recognized-output rules with their evidence. Default: unknown capability means no product-input support, refused by name, and no recognized intermediates.
- **CS5 Preparation.** RES composes `ViewOperationSource` functions inside its completion transaction: each operation-owning feature provides a crate-private catalog function returning the Running operations that affect a View. PREP provides `running_preparations(conn, view_id)` for Running prepare and Retry operations; open verification mutates nothing and does not block. PREP's review and prepare must accept product items: Result ID, path and acceptance digest. Default: the RES integration owner adds a product item variant to PREP's items. PREP's existing mode and footprint rules handle it, and PREP rehashes each product through `Catalog::result_proof` immediately before the effect (D19).
- **CS6 STO.** STO adds `running_storage_for_view(conn, view_id)` as a `ViewOperationSource` function for its Running storage mutations. Its custody adapter for Results wraps two RES reads: `Catalog::discovered_outputs`, with output class, write state, acceptance, recognition evidence and fingerprint, and `Catalog::accepted_results`, with each product's `dependentViews[]`. STO places accepted products in protected Keep and never changes Result records. Its reviewed cleanup and its archive and filing reference repair never call `require_view_open` and never write completion rows. Default: until 071 lands, only preparations block completion, and the STO parts of RES-AC-07, RES-AC-08 and RES-FR-04 are verified with 071.
- **CS7 PRJ.** 065 R13 reserves `acceptedProducts` on `project_detail` for RES. RES adds that field, read through the View's Project ID, and reads Project framing Targets for Target context.
- **CS8 CAL.** Calibration matching and assignment apply to light sessions only. Product inputs never receive calibration assignments. CAL owns generated-master detection and adoption (H4). The 068 planner detects masters from header evidence and needs the files of View output folders. RES therefore exposes the neutral read `Catalog::discovered_outputs(view_id: Option<Uuid>)`, listing each discovered file with its View, path, fingerprint, type, full adapter `CaptureMetadata`, availability and write state. CAL applies its own master rules to it with the View as origin and rehashes before adoption (D05). RES never classifies, preselects or adopts masters, offers no Add to calibration library action, and acceptance never implies adoption.
- **CS9 PIX.** Inspecting a Result image may use a PIX preview of a file path if PIX exposes one. Backend acceptance does not depend on it.
- **CS10 LIB.** Target context reads Confirmed Target associations of member sessions. Verified remap keeps asset identities and View membership (LIB-FR-07, LIB-AC-11) and leaves completion unchanged.

## Resolved ambiguities

Each entry records the decision, its basis and the alternative considered. Where the spec is silent, the default follows the root [decision register](../063-clean-rebuild-contract/decisions.md).

- **R1 Storage and schema version.** RES tables live in `crates/persistence/library/src/results.sql`, appended to the catalog schema, with SQL in `src/results.rs`. RES depends on LIB (064, version 6), PRJ (065, version 7), VSEL (066) and PREP (069), and lands after them in the order 064, 065, 066, 067, 068, 069. Its schema version is the version recorded by the last spec landed before it, plus one. An older catalog is refused like any other version, and development catalogs are reset under the autonomous objective. Basis: one writer and one reader snapshot for joins of Results, Views, Projects and Targets. Alternative: a separate crate needs a second writer.
- **R2 Folder roots.** Result files live under folders that are not library locations. The model gains `FolderRoot {id, path, identity}`, and `Location::root()` returns the root of a location. `inventory::scan`, `SourceProbe::root_identity` and the private `SourceRoot` take a `FolderRoot`. RES reuses the verified no-follow walk and byte-proof path. Result files never become library assets, and RES needs no Results-role library location. Alternative: a second walker and hasher would duplicate custody-critical code.
- **R3 Discovery trigger.** Opening Results calls `results_discover`, which walks the output location off the UI thread and commits one transaction. RES runs no watcher; reads of the listing access no file. Basis: H1 places discovery on Open Results. The 064 scan model keeps reads free of filesystem access. Alternative: the legacy watcher keeps background state and infers lifecycle from events.
- **R4 Pending.** A file reads Pending when its fingerprint at the walk, at the start of the settle window and at its end are not all equal, or when it vanished during the window. The window defaults to 2 s, a request may set it, and the response reports it. A Pending file is refused for acceptance and becomes settled on a later discovery. Basis: the spec states no detection rule. A shown observation window guesses no tool state. Alternative: the legacy size-only debounce misses rewrites of equal size.
- **R5 Recognized outputs.** A file is recognized only when a recognized-output rule of the View's profile matches its path below the output location (CS4). The rule supplies its role: `intermediate_calibrated`, `intermediate_registered`, `intermediate_other`, `temp_cache` or `log`. Every other file, including unknown files, is a candidate. Each recognized file carries its role, rule ID, profile and evidence, as Constitution II requires for inference. Classification never blocks acceptance. Alternative: the legacy fallback to Intermediate would hide an unrecognized product.
- **R6 Type and header evidence.** Type is FITS, XISF, TIFF or other, named by extension. FITS and XISF files keep the full adapter `CaptureMetadata` from the walk; the listing summarizes `IMAGETYP`, `FILTER`, dimensions and stack count. The 068 planner adds `stackCount` (`STACKCNT`, else `NCOMBINE`) to `CaptureMetadata`, and RES reads it from there. A stack count is a header count and never input-frame lineage. Header values never set a kind.
- **R7 Attach.** Attach takes a native path to a regular file and a kind. The core probes the file without following links and records its qualified volume and file identity and its parent folder identity as the root. A file on a volume without qualified identity is refused with IdentityConflict, because D19 needs a recorded identity. One Result exists per View and path; attaching the same path to the same View again is Conflict naming the existing Result.
- **R8 Lineage.** Provenance records two facts. The View association has basis `output_location` for a discovered file and `user_linked` for an attached file. Input-frame lineage is `unknown` for every Result in this version, because no profile has a qualified reader of tool-recorded input lists (CS4). No field states or implies that the planned membership was used. Acceptance, verification and reuse change neither fact. A later version may add a Tool-recorded state with its own qualified evidence. Alternative: deriving lineage from the prepared membership is the claim RES-FR-03 forbids.
- **R9 Kinds.** Kinds are `final_image`, `linear_integration`, `channel_product`, `mosaic_panel` and `other` with a required label. The user chooses the kind at attach or acceptance.
- **R10 Acceptance.** Acceptance appends a decision bound to freshly hashed bytes and their fingerprint (D19), against the expected decision revision and fingerprint. Pending, Offline, Missing and changed files are refused. Accepting current bytes again is the explicit drift review that D19 allows. The spec defines no withdrawal, so the plan adds none.
- **R11 Keep.** An accepted Result reads `cleanupDefault: keep`. STO owns cleanup groups and removal (CS6).
- **R12 Project and Target context.** An accepted Result appears on Project P when its View's Project is P. It appears on Target T when T is the View's originating Target, a framing Target of the View's Project, or the Target of a Confirmed association of a current member session. Each listing names its basis. Suggested associations never count, and nothing is inferred through product inputs. `results_create_view` takes an optional Project and infers none.
- **R13 Product inputs.** Product input rows name the product View, Result, acceptance decision and originating View. Each row is valid from the membership revision that added it until a revision removes it, so VSEL revisions that change only sessions keep them. Assigning a product rehashes its bytes, which must match the acceptance digest; Offline or changed bytes block with the drift named (D19). Product inputs carry no frames, and View, Project and Target totals never count them. Raw and product inputs may share a View record. Preparation needs the profile's mixed support.
- **R14 Drift on read.** Reading a View's product inputs takes one no-follow stat probe per input and hashes nothing. A changed stat reads `drifted`. An equal stat reads `current` with the last verification time, never a fresh match. Verification, assignment and preparation hash. A newer acceptance of the same Result reads `superseded` until an explicit update names it.
- **R15 Completion.** Completion rows are append-only: Complete or Reopened, with the View's membership and preparation revisions at that time. Mark Complete reads the Running operations of this View inside its writer transaction and is Conflict naming each one. It needs no Result, reads no file, removes nothing and starts no cleanup. External launch, exit or process state never enters it.
- **R16 Revisions.** Each Result has a decision revision for kind and acceptance. Each View has a completion revision for Complete and Reopen. Product input changes create a VSEL membership revision.
- **R17 Naming.** Commands use the `results_` prefix in `commands/results.rs`. Legacy `artifact_*` commands stay unregistered in the isolated shell.
- **R18 References.** RES records no library asset IDs in this version, so it registers no `AssetReferences` source. Retire review lists Result as not consulted. The LIB-AC-16 fake Result source stays as that test's model of a future lineage source.
- **R19 Errors.** RES adds no `LibraryError` variant. Stale input, a Complete View, a Running blocker and a Pending file are Conflict. An unsupported product input is InvalidInput naming the Result and kind. An unqualified volume is IdentityConflict, an unavailable file SourceUnavailable, and a failed write PersistenceFailure.
- **R20 Paused preparations.** RES-FR-07 blocks completion only for Running operations, so a Paused, Partial or Canceled preparation does not block it. Retrying such a preparation on a Complete View is refused until Reopen (CS2).

## Open questions

- Product-input capability of Siril, PixInsight/WBPP and SETI Astro Suite Pro (J26 G2) decides which branch of J26/S5 applies. Without PREP capability evidence every product View preparation is refused by name.
- Recognized-output rules need PREP fixture qualification per profile. Without them every output file stays a candidate, and the intermediate part of RES-AC-01 is an acceptance gap.
- An overwrite that keeps size and mtime is not visible to a stat probe. It reads `current` with its last verification time until verification or preparation hashes it.
- J26 G3: mixed raw and product inputs and **Add accepted results** in an existing View have no journey step.

## Qualification

Generated FITS and XISF stacks with `STACKCNT`, TIFF-named files, a log, an unknown file and a file that a helper thread appends to must cover discovery. Fixtures also need an unreadable subfolder, a link, an offline output root and an attached file outside it. They need a real PREP preparation for the blocker case, a second unrelated View, an overwritten accepted product and SQLITE_FULL. Every scenario compares source and output hashes before and after. Real development-MCP evidence remains an acceptance gate. No legacy test result proves the rebuild.
