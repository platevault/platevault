# Storage custody research

## Decision

Store cleanup and transfer reviews, operations, per-item phases and path claims as Tier 1 records in the clean library catalog, `crates/persistence/library`, through its single serialized writer. Put filesystem effects in a new `platevault_core::custody_fs` module and the pure selection, proof and layout rules in `platevault_core::custody`. A `platevault_core::storage` service runs operations off the UI thread. The isolated rebuilt shell exposes `storage_*` commands. The plan reuses no legacy executor, plan table or command.

## Source evidence

Read at `97ca51be39cf970be23e22fcbf22c60c7963b40c`, the reviewed 064 backend plus the 065 plan. No runtime behavior is claimed from reading.

- Catalog durability: one writer with WAL, FULL synchronous and macOS fullfsync, and a read-only pool (`crates/persistence/library/src/lib.rs:324-351`). `write_txn!` runs `BEGIN IMMEDIATE` and commits (`lib.rs:52-65`).
- Schema versioning: `SCHEMA` is `include_str!("schema.sql")` and `SCHEMA_VERSION` is 6 (`lib.rs:45-46`; `schema.sql:8-16`). `install_schema` refuses any other recorded version and has no migration chain (`lib.rs:2066-2102`).
- Operations: `scan_operations` has no kind column (`schema.sql:39-61`). `recover_interrupted` finalizes Running scans as Partial at open (`lib.rs:2104-2124`). `running_operation` reads only Running scans; `begin_scan` and `retire_location` call it (`lib.rs:3569-3576`, `:606`, `:2001`).
- Reviewed plans: remap reviews are durable rows that apply rechecks (`schema.sql:276-289`; `lib.rs:1823-1888`). `apply_remap_rows` keeps asset IDs, rebinds quality bases whose fingerprint matched and calls `rebind_association_bases` (`lib.rs:5940-6033`). Retire reviews re-read every reference on confirmation (`lib.rs:1976-2022`).
- Hashing: `current_digest` probes, hashes and re-probes a source against its recorded observation (`lib.rs:6097-6122`). `hash_contained` and `open_contained` hash a regular file opened without following links at any level (`lib.rs:6127-6153`, `:6207-6285`). `verify_digest` binds a fresh digest (`lib.rs:1185-1219`).
- Duplicates: `copy_links` records `identical` and `candidate` pairs (`schema.sql:150-158`). `ApplicableQuality::ConflictingCopies` labels diverged copies (`crates/platevault-model/src/lib.rs:357-377`). The catalog has no public library-wide duplicate listing.
- Identity: `observe_root_identity`, `validate_location_root` and `probe_fingerprint` live in `crates/platevault-core/src/inventory.rs:56-103`. Volume probes per platform are in `inventory/identity.rs:173-211`, `:220`, `:338`, `:396`. `VolumeIdentity` holds filesystem type and stable ID, never the mount path (`model/src/lib.rs:218-226`).
- Reference seam: `AssetReferences` and `Library::register_references` exist; Retire review names View, Project and Result records (`crates/platevault-core/src/library.rs:32-46`, `:194-241`; `model/src/lib.rs:962-985`).
- IPC: handlers return `Reply<T> = Result<T, ErrorResponse>` through `fail` and `report` (`apps/desktop/src-tauri/src/commands/library.rs:28-50`). The isolated shell registers handlers in `generate_handler!` and binds the dev bridge to loopback (`library_shell.rs:72-98`, `:162-188`). Legacy `cleanup_*` and `archive_*` commands exist in `commands/cleanup.rs` and `commands/plans.rs`.
- Legacy executor: `fs_executor` depends on `domain_core` and `project_structure` (`crates/fs/executor/Cargo.toml:10-32`). Its move copies without fsync or a destination re-read (`ops/move_op.rs:56-72`, `:175-197`). `trash_file` checks neither Trash support nor link type (`ops/trash_op.rs:116-145`). A permanent delete stays reachable (`ops/delete_op.rs:25-58`; `run/dispatch.rs:70-74`). `volume_check.rs:46-55` reads free space through `fs4`.
- `trash` 5.2.6, the workspace dependency (`Cargo.toml:121`): it canonicalizes only the parent, so a leaf link is trashed itself (`src/lib.rs:228-258`). macOS defaults to the Finder method, which needs Automation permission, and passes no resulting URL to `trashItemAtURL` (`src/macos/mod.rs:13-48`, `:100`). Linux falls back to `std::fs::copy` and removal across devices, which follows a link source (`src/freedesktop.rs:560-580`). Windows sets `FOF_NO_UI | FOF_ALLOWUNDO | FOF_WANTNUKEWARNING` (`src/windows.rs:44`).
- Lock file: `fs4` 1.1.0, `libc` 0.2.189, `objc2` 0.6.4 and `objc2-foundation` 0.3.2 are already locked.
- Frontend: the rebuilt commands have no TypeScript callers. Frontend acceptance stays a separate task, as in 064 and 065.

## Resolved ambiguities

Each entry records the decision, its basis and the alternative considered. Where the spec is silent, the default follows the root [decision register](../063-clean-rebuild-contract/decisions.md).

- **R1 Storage.** STO tables live in `crates/persistence/library/src/storage.sql`, appended to `SCHEMA`, with SQL in `src/storage.rs`. Basis: an item's phase, its path claims and the asset repoint must commit in one writer transaction. Alternative: a separate persistence crate would need a second writer or public library internals.
- **R2 Schema version and order.** STO depends on 064, 065, VSEL (066), CAL (068), PREP (069) and RES (070); PIX (067) and PLAN (072) are not dependencies. 064 records version 6 and 065 plans 7. STO sets `SCHEMA_VERSION` to the version after the one recorded when its last dependency lands, and an older catalog is refused and reset like any other version.
- **R3 Filesystem primitives.** A new `custody_fs` module owns Trash, verified copy, same-volume links, reference repair, free space and writability. It reuses the `fs_pathsafe` link classifier, the inventory identity probes and the catalog's contained hashing. `fs_executor` is not reused: it has no verified transfer, keeps a reachable permanent delete and pulls legacy domain crates.
- **R4 OS Trash.** Unknown support counts as unsupported, and a refused item stays in place. macOS calls `NSFileManager trashItemAtURL` through `objc2-foundation` and keeps the resulting URL as evidence; review rates a volume supported only when it is local, writable and of a qualified filesystem type. Linux moves the item into the freedesktop.org Trash on the same filesystem with a no-replace rename and never copies. Windows reads unsupported, reason `platform_unqualified`, until a qualified Recycle Bin implementation proves recycling. Alternative: `trash` 5.2 loses the macOS resulting URL and may copy through a link on Linux.
- **R5 Cleanup scope.** View cleanup needs a Complete View. Before Complete, only entries of replaced preparation revisions, those with PREP's `supersededBy` set, are in scope (D09, STO-FR-10). The scope is the View folder and its recorded output location; a Direct-source View has only its output location. A library asset of a Captures or Calibration location is in no group. Walks never follow links, and a directory is never an item.
- **R6 Roles and preselection.** PREP, RES and CAL records give each file's role with its recognition evidence. A RES `candidate` and any file no record names read Unknown. Recognized intermediates and temporary files are preselected. Prepared entries, verified duplicates, logs, manifests and Unknown files start unselected. Accepted products, candidate or adopted masters and generated sources retained after adoption are protected Keep (CAL-FR-07). A file RES reports with write state pending is blocked.
- **R7 Retained-original proof.** Removing a prepared copy, patched copy, clone, staging leftover or hardlink needs its original: a registered Active copy of the capture outside the cleanup scope. The original's current identity and SHA-256 must match the source digest PREP recorded, at review and again before the Trash call. A hardlink also needs its original path to resolve to the recorded file identity. An offline or unreadable original blocks the entry as an unavailable source. A verified duplicate or a retained adoption source names its kept copy, a file in an Active registered location. The kept copy's current identity and SHA-256 must equal the entry's at the same two points. A link entry holds no bytes and needs no byte proof.
- **R8 Basis for cleaned entries.** Review hashes every selected regular file and records the digest as the plan basis (D19). Before each Trash call the entry's identity and SHA-256 must match again. A link entry matches by no-follow identity and link text. Preview reads recorded evidence only and starts no hash.
- **R9 Blockers.** Stale identity, insufficient proof, an unavailable source, ambiguous ownership, unsupported Trash and a protected file without explicit selection each block their item. Ownership is ambiguous when another View's records, an unfinished operation or two records with different roles claim the path. A Results-location asset under a View root is not ambiguous by itself. Cleanup confirmation runs only unblocked items; blocked items stay and are named in the summary.
- **R10 Reclaim.** Each entry shows its size and a reclaim class: expected, shared link, link only or not guaranteed. A hardlink frees bytes only when no other name remains, and a clone may share blocks. Observed reclaim is the measured free-space change of the source volume; the OS Trash keeps bytes until it is emptied.
- **R11 Transfer scope.** Archive takes sessions from Storage and filing takes sessions from Sessions. Each moves every current member asset of those sessions; an unavailable member is a `source_unavailable` blocker, never silently left out. The destination is a folder inside an Active registered location with the sources' role. An unregistered destination is refused and names `library_register_location`, because STO-AC-07 needs archived inputs to read Offline. A different volume or root at the registered path is IdentityConflict.
- **R12 Verified transfer.** Review rehashes each source as the snapshot (D06, D19). Apply creates the destination with `create_new`, so a collision never overwrites. It copies, flushes the file with `F_FULLFSYNC` on macOS and `sync_all` elsewhere, flushes the parent directory, then re-reads and hashes the destination. On one volume with hardlink support, filing links the destination to the source and verifies the file identity and digest. Each phase intent commits before its filesystem action.
- **R13 Phases and commit points.** An item passes `destination_written`, `destination_verified`, `references_updated` and `source_retired`. The asset is repointed to the destination, with its ID kept, in the transaction that records `references_updated`. Retirement rehashes the source against the snapshot and moves it to the OS Trash. Source drift keeps both versions for review. Unsupported Trash ends the item as source retained.
- **R14 References.** View membership, Project links and Result lineage name asset IDs, so a repoint leaves them unchanged. Prepared entries and Direct-source handoff files hold paths. PREP never rewrites an entry, so STO repairs them and records the outcome against PREP's entry ID. STO writes a new link or handoff file at a sibling name, checks the entry for drift without following links, then renames the new one over it. Only app-written link and handoff entries are replaced this way. A same-volume hardlink entry already shares the destination's file. A cross-volume hardlink needs the user's choice of link or keep local copy, and a copy or clone entry needs no change. Every reference reports completed, blocked or uncertain.
- **R15 Approval.** A transfer starts only when its review has no blocker. A collision, missing mode choice, identity conflict, short free space or unavailable source requires a revised plan. Basis: J30/S2-S3 and STO-AC-06. Cleanup differs: blocked entries stay while the others proceed (J27/S7-S8).
- **R16 Retry.** Retry revalidates the destination volume and root, each source against its snapshot and each written destination against its recorded file identity. It resumes from the recorded phase. A partial destination file is reused only when its identity matches the recorded operation entry; otherwise the item is blocked. A name alone never proves anything. The spec defines no abandon action, so an unfinished item keeps its claims.
- **R17 Filing layout.** The default destination path is the asset's relative path below the chosen destination folder. Basenames never change. The user revises the plan by removing sessions, choosing another folder or giving one item another folder.
- **R18 Library interplay.** A scan skips paths claimed by an unfinished STO item and names them as an incomplete scope. Retire location and remap apply return Conflict while an unfinished STO item touches the location. `Catalog::open` marks Running storage operations Interrupted and in-flight items Uncertain. `Storage::recover` then records what each claimed path holds and resolves nothing.
- **R19 Storage overview.** The overview is read-only and starts no hash. It lists locations with availability, View footprints from PREP, RES and CAL records and no-follow metadata, and duplicate groups of identical, candidate and conflicting copies with no removal action. It also lists transfer operations with phase counts.
- **R20 Naming.** Commands use the `storage_` prefix in `commands/storage_custody.rs`, because legacy `cleanup_*` and `archive_*` commands exist.
- **R21 Restore.** Restoring relies on the OS Trash (D16). The NSFileManager path may not show Finder's Put Back; dragging the item out of the Trash still restores it. The Finder method is rejected because it needs Automation permission.

## Cross-spec seams

VSEL, CAL, PREP and RES land before STO, so STO adapts their published catalog reads in one reader snapshot instead of defining a trait for them to implement. X1 to X5 were agreed with each planner on 2026-10-05. If a read differs when 071 is implemented, the 071 adapter maps it and the stricter outcome applies: an unnamed file reads Unknown, and an unproven reference blocks retirement.

- **X1 VSEL (066).** `Catalog::view(id) -> ViewRecord` supplies the name and latest committed revision, and `ViewReferences` is the View `AssetReferences` source. Membership stores asset IDs per D16 capture, so a repoint changes no View row and yields no refresh item. An unknown View is NotFound.
- **X2 PREP (069), facts.** `Catalog::prepared_entries(preparationId)` returns entries `{entryId, assetId?, role, kind, path, linkTarget?, sourceSha256, entrySha256?, identity}`, where `identity` is the no-follow `ObservationFingerprint`. The kinds are symlink, hardlink, copy, clone, patched copy, Direct-source, input list and staging. Each preparation revision carries the View folder and output folder with their identity, and `supersededBy` once a newer revision of the same View reaches Prepared. PREP never removes, trashes or rewrites an entry.
- **X3 PREP (069), handoff paths and Open.** PREP's pure `render_handoff_file(spec, pathMapping) -> bytes` in `platevault_core` returns a Direct-source or input-list file with new paths; STO writes and verifies it. PREP's Open and verification read `Catalog::entry_custody(preparationId)` as a 071 extension: a removed entry blocks Open, and a repaired target counts only as STO recorded it. Default: a path the renderer cannot rewrite reads blocked, reason `config_update_unsupported`, and its source is never retired.
- **X4 RES (070).** `Catalog::discovered_outputs(viewId)` returns output class, write state, acceptance, the no-follow fingerprint, and either `recognized {role, ruleId, profileId, evidence}` or `candidate`. Recognized roles come only from PREP output rules: the three intermediate kinds, `temp_cache` and `log`. `Catalog::accepted_results(AcceptedScope::View(id))` adds `dependentViews`. RES's completion record supplies Complete. 071 adds crate-private `running_storage_for_view(conn, viewId)` and calls it inside RES's `running_view_operations`, so Mark Complete is blocked in the same transaction (RES-AC-07).
- **X5 CAL (068).** `Catalog::calibration_custody_facts(viewId)` names adopted masters, candidate masters among RES outputs, and generated sources retained after adoption. A retained source's kept copy is `{masterId, locationId, relativePath, fingerprint with contentSha256}`, with `assetId` only after a scan indexed it. A source whose adoption failed stays a candidate master.
- **X6 PRJ (065).** The planned `ProjectReferences` source names Projects in STO-FR-02. Default: STO lists the consulted kinds, so an unregistered kind is shown as unchecked, never as no reference.
- **X7 Fingerprint-bound bases.** A repoint changes file identity and keeps the digest. STO rebinds library quality and association bases as remap does and records each repoint with old and new fingerprints. Default: a feature that binds file identity reads drift until it rebinds through `Catalog::asset_repoints`, failing safe.

## Qualification

Generated FITS/XISF and volume fixtures must cover:

- A Complete View with 208 hardlink entries, a link entry, a copy entry and recognized intermediates.
- An accepted product used by another View, an adopted master with its retained source, and an unknown file.
- A deleted original behind a hardlink, and an unwritable prepared folder.
- A second disk image under the same mount name, and a volume whose Trash probe is unsupported.
- A destination that disconnects mid-copy, and a destination byte change before its re-read.

Tests that touch a real OS Trash run only in an isolated account or disposable VM. Every scenario compares source hashes before and after, and real development-MCP evidence remains an acceptance gate.
