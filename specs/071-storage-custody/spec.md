# Feature Specification: Storage operations: run Clean up, verified archive, Project archive and Trash, Import

**Feature Branch**: `063-clean-rebuild-contract`

**Spec ID**: `071-storage-custody`

**Created**: 2026-10-03

**Status**: Draft; product defaults and all human-approval gate waivers follow the root autonomous objective. Requirements analysis, implementation and verification remain required.

**Input**: Clean rebuild with selective reuse of verified code and the agreed PlateVault product flow.

## User Scenarios & Testing

### User Story 1 - Storage operations: run Clean up, verified archive, Project archive and Trash (Priority: P1)

Selectable Clean up of a processing run (View) to the OS Trash with retained-original proof, plus verified archive transfers that rebuild affected run references and never retire a source before verification. When a Project is Done, this feature executes the custody steps of its Done / Archive sheet, which PV-PRJ owns. It archives the sessions no other open Project uses. It also moves the Project's rejected frames and its processing intermediates to the OS Trash under the same custody rules.

**Why this priority**: This feature owns the workflow steps listed below without imposing unrelated product features.

**Independent Test**: Exercise the acceptance scenarios through the running product with isolated inputs. Existing baseline code does not prove the redesigned behavior.

**Acceptance Scenarios**:

- **STO-AC-01**: Given a Complete run whose preparation revisions created symlinks and copies. Its Results folder holds intermediates, an accepted Result and an unknown file. When Clean up opens, then the symlink and copy groups are listed and preselected. The intermediates, the Result and the unknown file stay off the list. Deselecting a group keeps its entries out of the review. (D-W3, D-W26)
- **STO-AC-02**: Given a Direct-source run, when its cleanup preview opens, then original subs appear in no cleanup group. (D-W3)
- **STO-AC-03**: Given a location where OS removal deletes immediately, when Send to Trash runs, then those files are refused and listed as blocked with Keep files and Reveal location, and nothing is permanently deleted.
- **STO-AC-04**: Given a prepared hardlink holds the last bytes after its original was deleted externally, when its removal is reviewed, then insufficient retained-original proof blocks removal.
- **STO-AC-05**: Given an archive destination fails hash verification or disconnects during transfer, when the operation settles, then the source is retained. Destination-verified, source-retained, reference-updated, pending and uncertain phases are distinguished. Retry resumes recorded work after revalidating identities.
- **STO-AC-06**: Withdrawn (D-W11). "File into library" is dropped, and STO-IMP-AC-06 covers Import destination collisions.
- **STO-AC-07**: Given a completed archive later disconnects, when its run is opened, then totals and membership remain unchanged and archived inputs show Offline. Preparing those inputs is refused. (D-W3)
- **STO-AC-08**: Given an approved prepared symlink and a verified duplicate, when they are sent to Trash, then the symlink target remains byte-identical and the duplicate action names the verified copy kept. No target directory is followed.
- **STO-AC-09**: Given mixed successful and blocked Trash items, when execution settles, then an exact partial summary names both sets and the run records removed and remaining entries; unsupported Trash removes zero files even after approval. (D-W3)
- **STO-AC-10**: Given archive reference repair fails, then source retirement is blocked and each reference is marked blocked or uncertain. A different destination volume at the same mount path is a conflict, and a cross-volume hardlink requires a separately approved supported mode. Direct-source configuration paths show their individual update status.
- **STO-AC-11**: Given replaced prepared entries before processing is Complete, when removal is reviewed, then the same per-item retained-original proof, protected products, no-follow and OS Trash rules apply. Unapproved or unproven entries remain.
- **STO-AC-12**: Given registered online/offline locations, run preparations, duplicate content and archive transfers, when Storage opens, then location availability, run footprints, content-identity duplicate candidates and transfer phases are shown separately. Candidate display never authorizes removal. (D-W3)
- **STO-AC-13**: Withdrawn (D-W11). Filing selected Sessions into a library layout is dropped, and Import previews templated destinations instead (STO-IMP-AC-01).
- **STO-AC-14**: Given an archive or Import Move item whose source bytes change after its snapshot is copied and destination-verified, when retirement is reached, then the current source identity or SHA-256 fails comparison with that snapshot. The item is blocked with drift named, both versions are retained and other items keep their recorded phases. A final destination or reference re-verification failure also retains the source. Retry requires reviewed current evidence, never automatic retirement of either version. (D-W11)
- **STO-AC-15**: Given an approved cleanup plan or Import, when a selected item changes in place before execution with its size and mtime preserved, then that item is blocked with drift named and left in place. The same holds when the retained original or kept copy it relies on changes. Other approved items proceed, and the summary names the blocked item. (D-W11)
- **STO-AC-16**: Withdrawn (D-W11). Same-volume filing of indexed files is dropped. Import skips files already in the library by SHA-256, so it never moves a file a run references.
- **STO-AC-17**: Given Project A is marked Done and its runs use sessions S1 through S4. S2 is also a member of a run in Project B, which is not Done, and S3 is only a candidate of open Project C. When the user reviews and approves Archive on the Done / Archive sheet, S1, S3 and S4 transfer under STO-FR-07 to paths laid out by the naming templates. S2 stays at its path and is listed as kept because Project B uses it. Project B's run membership and totals are unchanged. (D-W26, D-W20, D-W46)
- **STO-AC-18**: Given Project A is Done with 40 candidate frames whose library quality is Unusable, plus 6 frames rejected for Project A only. Of the 40, 3 are in a prepared revision of a Project B run at Prepare, 4 are in a prepared revision of an Abandoned run, and 2 others are recorded inputs of a Result. When the Done / Archive sheet opens, it offers "Move 35 rejected frames to Trash (size)", which includes the Abandoned run's 4. The 6 Project-only rejects are not counted or listed. The 5 refused frames are listed with their reasons. (D-W43, D-W42, D-W71)
- **STO-AC-19**: Given the user has approved moving the 35 frames, one frame's bytes change in place with size and mtime preserved before it moves. Another frame sits on a location where OS removal deletes immediately. When the move runs, both are refused with the reason named and left in place. The other 33 go to the OS Trash and nothing is permanently deleted. The summary names moved and refused frames, and the library marks the 33 Trashed (LIB-FR-18). (D-W43)
- **STO-AC-20**: Given a Complete run whose sessions include library-Unusable frames, when its Clean up opens, then no original frame appears in any cleanup group. Moving rejected frames to Trash is offered only on the Project's Done / Archive sheet, not on a run or in Sessions. (D-W43, D-W26)
- **STO-AC-21**: Given a Done Project whose runs' Results folders hold 120 recognized intermediates, an accepted Result, an adopted master's generated source and an unknown file. One intermediate is on a location with no Trash. When the Done / Archive sheet opens, it offers "Move 120 processing intermediates to Trash (size)": the other 119 intermediates plus the generated source, which is listed as a verified duplicate that names the kept library copy. It lists the refused intermediate with its reason. The Result and the unknown file are not offered. After that one approval the 120 go to the OS Trash and nothing is permanently deleted. (D-W70, D-W43)
- **STO-AC-22**: Given Project A was Done and its Archive moved S1 and S3 to the archive location, when the user reopens Project A, then no file moves. S1 and S3 show as Archived at their archive paths until the user restores them through a reviewed transfer. (D-W69)

### User Story 2 - Import (Priority: P1)

Bring frames from any card, disk or OS-mounted network folder into library storage, Lightroom style. The user picks a source, sees each file's templated destination in Captures or Calibration storage, and chooses Copy or Move. Import holds back duplicates, untyped frames and files still being written. Organized archives are added in place instead. Import replaces "File into library", and the app has no Inbox.

**Why this priority**: Import is how new captures reach the library for every later step, so it ships with the storage custody rules it depends on.

**Independent Test**: Import isolated fixture sources onto isolated Captures and Calibration locations through the running product, then compare source and destination bytes, the import summary and the library catalog.

**Acceptance Scenarios**:

- **STO-IMP-AC-01**: Given an SD card holds Ha lights of NGC 7000, flats, darks, two frames with no frame type, and one file still being written, the user picks it as an Import source. The preview then lists each light under its templated path in the chosen Captures location, such as `NGC7000/Ha/2026-04-12/light/`. Each flat and dark is listed under its per-type path in the Calibration location. The two untyped frames are listed as Unclassified and held for a type, and the growing file is listed as waiting to settle. Nothing is written before the user starts the import. (D-W11, D-W20, D-W24)
- **STO-IMP-AC-02**: Given Copy is chosen, when Import runs, then every destination is written, re-read and matches the SHA-256 of its source snapshot, and every source is unchanged. (D-W11)
- **STO-IMP-AC-03**: Given Move is chosen, when Import runs, then each source goes to the OS Trash only after its destination verifies and the source still matches its snapshot. A failed verification keeps that source and names the item. A source on a volume with no Trash, or whose OS removal deletes immediately, is kept and reported as copied with the source kept. Nothing is permanently deleted. (D-W11)
- **STO-IMP-AC-04**: Given a saved source was last imported on 2026-09-28, and since then 20 new frames were written to it and 5 earlier frames were copied back under new names. When the user runs Import new, only the 20 are imported. The summary lists the 5 as duplicates skipped by SHA-256, and no second copy is created. (D-W11, D-W24)
- **STO-IMP-AC-05**: Given an already organized archive folder, when the user chooses Add existing library folder, then it is registered and indexed in place under LIB-FR-02, and no file is copied, renamed or moved. (D-W11)
- **STO-IMP-AC-06**: Given a templated destination path holds a file with different bytes, the preview blocks that item. PlateVault never overwrites the file, and the item stays blocked until the user changes the template or leaves the item out. A file with the same bytes at that path is a skipped duplicate. Other items proceed. (D-W11, D-W24)
- **STO-IMP-AC-07**: Given two Unclassified frames in the preview, the user sets one to flat and leaves the other unset. The flat then routes to its Calibration path and imports. The summary lists the other as held Unclassified and not imported. (D-W24)
- **STO-IMP-AC-08**: Given Settings > Naming, when the user changes the light template with the chip editor to `{target}/{date}/{filter}/`, then the live preview shows the sample path and names any fallback token it used. A template containing `..` or a reserved name shows an inline error and cannot be saved. Restore defaults returns the per-type defaults. The next Import and Archive previews use the saved template. (D-W20)
- **STO-IMP-AC-09**: Given a source on an OS-mounted network share, when the share is unmounted mid-import, then verified items keep their state and the source reads Offline. No source of an unverified item is trashed. When the share returns, Retry resumes the recorded work without copying verified items again and without relying on filename presence. (D-W11, D-W12)
- **STO-IMP-AC-10**: Given lights with no OBJECT and no other Target evidence, when they are previewed, then their `{target}` segment reads `unclassified` and the preview names that fallback. After import they appear in Sessions under "Needs a Target" (LIB-FR-17). (D-W20, D-W24, D-W35, D-W39)

### Edge Cases

The [root contract](../063-clean-rebuild-contract/spec.md) governs file custody, uncertainty, exact membership, failed writes, and independent lifecycle decisions. Each acceptance scenario tests observable outcomes; no mock acknowledgment counts as terminal success.

- A Done Project's Archive and its two Move to Trash offers run as separate approvals. A frame that a running archive transfer is moving is refused by Move to Trash until that transfer settles. (D-W70)
- When no Calibration location is registered, Import blocks only the calibration items and names the missing role; lights still import.

## Requirements

### Functional Requirements

- **STO-FR-01**: Once a run is Complete or Abandoned, its Clean up previews only the entries its preparation revisions created: prepared links, clones and copies (PREP-FR-14). It shows them in groups with counts, sizes, proposed actions and Inspect files, and the groups start selected, because Clean up removes prepared entries. Intermediates, logs, manifests, unknown files, accepted Results and candidate or reusable masters in the run's Results folder are never listed, and neither are original sources or library frames. Users can toggle groups and individual entries. Selecting a group never authorizes deleting a whole directory. (D-W3, D-W26, D-W71)
- **STO-FR-02**: Each file shows path, role, other run or Project references, retained-original evidence, and estimated bytes. Link sizes are never presented as guaranteed reclaim. (D-W3)
- **STO-FR-03**: Originals outside the run are protected. Direct-source originals are never candidates; a Direct-source run's Clean up lists nothing, because its preparation created no entries (PREP-AC-20). Library raw files are outside run Clean up; rejected originals reach the OS Trash only through the Project's Done / Archive sheet (STO-FR-14). (D-W3, D-W26, D-W43)
- **STO-FR-04**: Review cleanup lists exactly the selected and retained entries; the default action is Send to OS Trash. Removing a prepared copy or a hardlink needs verified retained originals; removing a duplicate names the copy kept. Review records each selected entry's identity and SHA-256, a link's identity and target path without following it, and the retained original or kept copy it relies on. Execution re-verifies them immediately before each move to Trash (D19). Trash support is shown per location with movable and blocked counts, and an OS action that deletes immediately counts as unsupported. Stale identity, drift, insufficient proof, an unavailable source, or ambiguous ownership stops the affected item. Link entries are trashed without following their targets.
- **STO-FR-05**: Trash execution shows progress, per-item outcomes, and an exact complete or partial summary, and the run records what was removed and what remains. Unsupported Trash refuses the item and offers Keep files or Reveal location. No permanent-delete fallback exists. Restoring relies on the OS Trash, with no guarantee once it is emptied. (D-W3)
- **STO-FR-06**: Archive stays available from Storage for selected sessions or retained data, and from a Done Project's Done / Archive sheet (STO-FR-13). Archive review shows destination paths laid out by the naming templates (STO-IMP-FR-07), bytes, source identities, affected runs, and reference updates. Membership and exclusions stay fixed. It also shows destination volume identity, free space, and writability; a different volume at the same path is a conflict. Each run's current and proposed reference mode is shown. A cross-volume hardlink is never rebuilt as a hardlink: the user chooses a supported mode or keeps the local copy, with no implicit conversion. (D-W3, D-W11, D-W20)
- **STO-FR-07**: Verified transfer copies a source snapshot, writes durably and re-reads the destination to compare hashes. Retire a source only when its current identity and digest match that snapshot, the destination re-verifies and every affected reference passes immediately before retirement. Any failed check blocks the item and retains its source; source drift retains both versions for review. References report completed, blocked or uncertain; Direct-source configuration paths name their update status. Expected and observed reclaim remain separate.
- **STO-FR-08**: If the archive is disconnected later, totals and membership are kept, inputs show Offline, and preparing or opening refuses rather than omits them. After an interruption the user sees destination-verified, source-retained, reference-updated, and pending work. Retry resumes the recorded work and never relies on filename presence. Failure sequencing follows D06 in the root decision register.
- **STO-FR-09**: Withdrawn (D-W11). "File into library" from Sessions is dropped. Import (STO-IMP-FR-01 through STO-IMP-FR-08) brings files into library storage, and "Add existing library folder" indexes organized folders in place.
- **STO-FR-10**: Replaced preparation entries may be removed before the run is Complete or Abandoned only through the same reviewed scope, retained-original proof, protected-product and OS Trash handling as run Clean up. Reprepare never bypasses custody rules. (D-W3, D-W71)
- **STO-FR-11**: Storage shows registered locations and availability, run footprints, library-wide content-identity duplicate candidates and archive transfers. LIB supplies location evidence. Candidate display does not authorize duplicate disposal; removal remains governed by reviewed custody scope. (D-W3)
- **STO-FR-12**: Destination collisions never overwrite. External drift in app-written references or operation entries is identified before mutation and blocks the affected stale item for review.
- **STO-FR-13**: After the user marks a Project Done (PV-PRJ), this feature executes the Archive that its Done / Archive sheet offers (PRJ-FR-14) for the Project's member sessions, the sessions in its runs. A session that PRJ-FR-14 keeps, because it is a member of a run in another Project not marked Done, stays at its path. The review lists it as kept and names the Project that uses it. The other sessions transfer under STO-FR-06 through STO-FR-08. Archive is optional, and a Done Project with no archive is valid. Archiving changes no run's membership or totals in any Project. After the Project is Reopened (PRJ-FR-14), its archived sessions show as Archived until the user restores them, and restoring moves files only through a reviewed transfer under STO-FR-06 through STO-FR-08. (D-W26, D-W46, D-W69)
- **STO-FR-14**: This feature executes the "Move N rejected frames to Trash (size)" offer of the Done / Archive sheet. Which frames the offer covers, and which it refuses with their reasons, follow PRJ-FR-15. This is the only way PlateVault moves a library frame to the Trash: it is not part of a run's Clean up and is not offered anywhere else. Size is the expected reclaim and excludes bytes still held by another hard link. Besides the PRJ-FR-15 refusals, the sheet lists every custody refusal under STO-FR-15 with its reason. The move is a separate approval from Archive and from the intermediates move of STO-FR-16. (D-W43, D-W42, D-W26, D-W70, D-W71)
- **STO-FR-15**: Moving rejected frames follows the cleanup custody rules. It acts only on copies in registered Captures locations, never on prepared links, clones or copies in run folders, or on files outside a registered location. Every physical copy of a frame moves; if any copy is refused, the whole frame is refused. Review records each copy's identity and SHA-256, and execution re-verifies them immediately before each move (D19). An Offline or unreadable location, drift, a stale review, or a location whose OS removal deletes immediately or has no Trash refuses the frame and leaves it in place. Files go to the OS Trash only, with no permanent delete and no fallback. Execution shows progress, per-frame outcomes and an exact summary of moved and refused frames. LIB marks moved frames Trashed (LIB-FR-18). Undo is Put back in the OS Trash followed by a rescan. The same custody rules govern the intermediates move of STO-FR-16. (D-W43, D-W57, D-W70)
- **STO-FR-16**: This feature executes the "Move N processing intermediates to Trash (size)" offer of the Done / Archive sheet. Which items it covers, keeps, refuses and counts in N follow PRJ-FR-15; accepted Results, adopted masters and candidate masters (CAL-FR-06) stay protected. An adopted master's generated source moves under the same approval as the intermediates, as a verified duplicate that names the kept library copy (STO-FR-04), and execution re-verifies that copy before moving the source. Review records each item's identity and SHA-256, and execution re-verifies it immediately before each move (D19). Besides the PRJ-FR-15 refusals, the sheet lists every custody refusal of STO-FR-15 with its reason. Files go to the OS Trash only, with no permanent delete. The move is a separate approval from Archive and from the frames move. (D-W70, D-W43)
- **STO-IMP-FR-01**: Import has its own workflow entry in main navigation and on Home. A source is any local folder, removable volume, or network path the OS has already mounted; PlateVault mounts nothing (LIB-FR-19). A source can be saved under a name. Import new on a saved source offers only files not already imported: a file whose SHA-256 matches a frame imported from that source or any indexed frame is skipped. "Add existing library folder" sits beside Import and registers an organized folder to index in place (LIB-FR-02), with no copy. Import replaces "File into library", and the app has no Inbox. Archive is unchanged and stays separate (STO-FR-06). (D-W11, D-W7, D-W12)
- **STO-IMP-FR-02**: Import classifies each source file by its frame-type header. Lights route to a Captures location. Darks, flats, bias frames and masters route to a Calibration location. A file with no frame type is Unclassified: it is held in the preview until the user sets a type, and it is never imported untyped. A file whose SHA-256 matches an indexed frame or another file in the same import is skipped as a duplicate and listed, and only the first copy is imported. A file whose size or modification time is still changing is held as waiting to settle and is offered once both stay unchanged across consecutive checks. When a role has several locations, the user chooses one for the import; when a role has none, its items are blocked with the missing role named and a way to register one (LIB-FR-01). (D-W24)
- **STO-IMP-FR-03**: Before anything is written, the preview lists every source file with its templated destination path, and counts and bytes per destination. It also lists duplicates, Unclassified and waiting-to-settle files, collisions, and each destination volume's free space and writability. The preview may name a light's confirmed rig. If the light's FILTER value then matches no filter on that rig, the preview shows the value as unknown with the "Add {value} to {rig}" prompt of PLAN-EQ-FR-04, and the prompt holds nothing back. The user chooses Copy or Move for the whole import. Starting the import approves only the displayed items and records each source's identity and SHA-256. (D-W11, D-W20, D-W24, D-W31)
- **STO-IMP-FR-04**: Copy uses verified transfer (STO-FR-07): it copies a source snapshot, writes durably, re-reads the destination and compares SHA-256, and leaves the source untouched. Move does the same, then re-verifies the source against its snapshot immediately before sending it to the OS Trash (D19). A failed destination verification keeps the source; source drift keeps both versions for review. If the source volume has no Trash or its OS removal deletes immediately, the source is kept and the item reports copied, source kept. Import never permanently deletes and never overwrites. (D-W11)
- **STO-IMP-FR-05**: A destination path that holds a file with different bytes blocks the item until the user changes the template or leaves the item out (STO-FR-12). A file with identical bytes at that path is a duplicate and is skipped. Templates set the folder path; files keep their original basenames. (D-W11, D-W24)
- **STO-IMP-FR-06**: Import shows per-item progress and outcomes and an exact summary. The summary counts imported items, skipped duplicates, held Unclassified and waiting-to-settle files, blocked items, failed verifications, and Move sources trashed or kept, and is recorded in Activity. Hashing a network source shows progress and resumes after an interruption (LIB-FR-19). After an interruption or an unmounted source or destination, verified items keep their state and the rest stay pending. Retry resumes the recorded work after revalidating identities and never relies on filename presence. (D-W11, D-W12)
- **STO-IMP-FR-07**: Naming templates are used by Import and Archive and return unchanged from the legacy app, with two exceptions. The legacy "Auto-apply pattern" checkbox and the generic project folder pattern are dropped, because runs own the output layout (PREP-FR-06). Nine tokens resolve from frame metadata, each with a fallback: `{target}` → `unclassified`, `{filter}` → `nofilter`, `{date}` → `undated` (ISO observing-night local date), `{frame_type}` → `unknown` (lowercase), `{camera}` → `unknown-camera`, `{exposure}` → `unknown-exposure`, `{gain}` → `unknown-gain`, `{binning}` → `1x1`, `{set_temp}` → `untempered`. Per-type defaults are light `{target}/{filter}/{date}/light/`, flat `flats/{filter}/{date}/`, dark `darks/{exposure}/`, bias `bias/`, master flat `masters/flats/{filter}/`, master dark `masters/darks/{exposure}/` and master bias `masters/bias/`. Only overridden types are stored. Settings > Naming edits each template with a chip editor of tokens, literals and the separators `/`, `-`, `_` and space. Validation runs in the editor and again when the template is saved or resolved, and shows errors inline. Resolution sanitizes names, rejects path traversal and reserved names, and caps lengths. Restore defaults is available. A live preview resolves the template against sample metadata and names every fallback token it used. (D-W20, D-W58)
- **STO-IMP-FR-08**: Imported files are indexed as they land under LIB-FR-16. Lights appear in Sessions and calibration frames in the Calibration library. Import changes no quality decision, Target or equipment association. (D-W24)

### Key Entities

Use the [root vocabulary](../063-clean-rebuild-contract/spec.md#key-entities). Feature-specific evidence and decisions retain their input identity, scope, and revision. This feature adds:

- **Processing run (View)**: the UI name for a View; it belongs to exactly one Project. This spec calls it a run, and its Clean up is the former View cleanup.
- **Done / Archive sheet**: the sheet a Project offers once marked Done, holding Archive, Move rejected frames to Trash and Move processing intermediates to Trash. PV-PRJ owns the sheet, its offers and their eligibility (PRJ-FR-14, PRJ-FR-15); this feature executes the approved custody steps. (D-W26, D-W43, D-W70)
- **Import source**: a folder or volume Import reads from, optionally saved under a name so Import new can skip files already imported.
- **Naming template**: a per-frame-type folder pattern of tokens, literals and separators, used by Import and Archive.

## Decisions before feature approval

- Root decisions D05, D06, D09, D14 and D16 define protected adopted-master sources, transfer phases, replacement cleanup, the collision and keep-source rules D14 passes to Import, and Storage candidate scope. D-W70 makes the intermediates move of STO-FR-16 the reviewed cleanup that D05 names for a generated master source. Whole-library duplicate disposal and application-managed restore remain outside run Clean up.
- Root decision D19 binds cleanup, archive, Import and Move to Trash to re-verified identity and SHA-256; D06 is its archive form.
- Workflow decisions D-W3, D-W7, D-W11, D-W12, D-W20, D-W24, D-W26, D-W31, D-W35, D-W39, D-W42, D-W43, D-W46, D-W57, D-W58 and D-W69 to D-W71 (settled 2026-10-06) set the run terminology and replace filing with Import. They also set network sources, naming templates, import routing and run Clean up limited to prepared entries. They set the custody steps of the Project Done / Archive sheet, which PV-PRJ owns. Those steps are the Archive transfer, restoring archived sessions after Reopen, and the moves of rejected frames and processing intermediates to the OS Trash. D-W71 gives an Abandoned run the same Clean up and trash gates as a Complete one. D-W11 replaces D14's reviewed filing with Import; D14's rule that a source is kept until its destination verifies carries into STO-IMP-FR-04.
