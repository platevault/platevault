# Feature Specification: Storage operations: View Clean up, verified archive, Wrap up Trash and Import

**Feature Branch**: `063-clean-rebuild-contract`

**Spec ID**: `071-storage-custody`

**Created**: 2026-10-03

**Amended**: 2026-10-14, to the F4 Project model, D-W93 to D-W106.

**Status**: Draft; product defaults and all human-approval gate waivers follow the root autonomous objective. Requirements analysis, implementation and verification remain required.

**Input**: Clean rebuild with selective reuse of verified code and the agreed PlateVault product flow.

## User Scenarios & Testing

### User Story 1 - Storage operations: View Clean up, verified archive and Wrap up Trash (Priority: P1)

Selectable Clean up of a Project's View to the OS Trash with retained-original proof, the removal of the old View after each Apply, and verified archive transfers that repoint affected View entries and never retire a source before verification. When a Project is wrapped up, this feature executes the custody steps of its Wrap up, which PV-PRJ owns: removing the View and whatever `View (previous)/` still holds in its Clean up step, the moves of the Project's rejected frames, `Processing/` files and duplicate copies to the OS Trash in its Trash step, and the transfer of the sessions no other open Project holds in its Archive step. A Closed or Archived Project is locked for good, so nothing here reopens it or restores its sessions (D-W97).

**Why this priority**: This feature owns the workflow steps listed below without imposing unrelated product features.

**Independent Test**: Exercise the acceptance scenarios through the running product with isolated inputs. Existing baseline code does not prove the redesigned behavior.

**Acceptance Scenarios**:

- **STO-AC-01**: Given Project A in Wrap up whose View is in Copies mode, and whose `View (previous)/` still holds a copy whose original an earlier Apply couldn't verify and a notes file the user left unticked in the Apply sheet. When the Clean up step opens, then it offers removing the View, ticked, and lists the two `View (previous)/` entries, unticked (provisional). Files in `Processing/` and `Output/`, originals and library frames stay off the list. For a View in Symlinks mode the View row starts unticked. Leaving a row unticked keeps its entries in place. (D-W3, D-W81, D-W97, D-W100)
- **STO-AC-02**: Withdrawn (D-W81). There is no Direct-source mode.
- **STO-AC-03**: Given a location where OS removal deletes immediately, when Send to Trash runs, then those files are refused and listed as blocked with Keep files and Reveal location, and nothing is permanently deleted.
- **STO-AC-04**: Given a copy in the View holds the last bytes after its original was deleted externally, when its removal is reviewed, then insufficient retained-original proof blocks removal. (D-W81)
- **STO-AC-05**: Given an archive destination fails hash verification or disconnects during transfer, when the operation settles, then the source is retained. Destination-verified, source-retained, reference-updated, pending and uncertain phases are distinguished. Retry resumes recorded work after revalidating identities.
- **STO-AC-06**: Withdrawn (D-W11). "File into library" is dropped, and STO-IMP-AC-06 covers Import destination collisions.
- **STO-AC-07**: Given a completed archive later disconnects, when the Archived Project or a duplicate of it is opened, then totals and membership remain unchanged and the archived inputs show Offline. The duplicate's Apply changes nothing and lists them as offline originals. (D-W3, D-W96, D-W100)
- **STO-AC-08**: Given an approved View symlink and a verified duplicate, when they are removed, then the symlink target remains byte-identical and the duplicate action names the verified copy kept. No target directory is followed.
- **STO-AC-09**: Given mixed successful and blocked Trash items, when execution settles, then an exact partial summary names both sets and the Project records removed and remaining entries; unsupported Trash removes zero files even after approval. (D-W3)
- **STO-AC-10**: Given archive reference repair fails, then source retirement is blocked and each reference is marked blocked or uncertain. A different destination volume at the same mount path is a conflict. A symlinked entry is repointed to the session's new path. (D-W81)
- **STO-AC-11**: Given Apply swapped in a new View for Project A, and `View (previous)/` holds 50 old copies and a notes file the user left unticked in the Apply sheet. One copy's original no longer matches its recorded digest, and the user edited another copy in place. When the cleanup after the swap runs, then the 48 verified copies are deleted outright, not sent to the Trash, and the unverifiable copy, the edited copy and the notes file stay in `View (previous)/`. Provisional: the Project shows what `View (previous)/` still holds, with Reveal and a reviewed Move to Trash. (D-W100)
- **STO-AC-12**: Withdrawn (D-W86). There is no Storage surface: Settings > Locations shows locations and their availability (LIB-AC-23), and the Sessions Duplicates filter shows duplicates (LIB-AC-24).
- **STO-AC-13**: Withdrawn (D-W11). Filing selected Sessions into a library layout is dropped, and Import previews templated destinations instead (STO-IMP-AC-01).
- **STO-AC-14**: Given an archive or Import Move item whose source bytes change after its snapshot is copied and destination-verified, when retirement is reached, then the current source identity or SHA-256 fails comparison with that snapshot. The item is blocked with drift named, both versions are retained and other items keep their recorded phases. A final destination or reference re-verification failure also retains the source. Retry requires reviewed current evidence, never automatic retirement of either version. (D-W11)
- **STO-AC-15**: Given an approved cleanup plan or Import, when a selected item changes in place before execution with its size and mtime preserved, then that item is blocked with drift named and left in place. The same holds when the retained original or kept copy it relies on changes. Other approved items proceed, and the summary names the blocked item. (D-W11)
- **STO-AC-16**: Withdrawn (D-W11). Same-volume filing of indexed files is dropped. Import skips files already in the library by SHA-256, so it never moves a file a View references.
- **STO-AC-17**: Given Project A in Wrap up, which holds sessions S1 through S4. S2 is also held by Project B, which is not Closed, and S3 is only a suggestion on open Project C. When the Archive step opens, S1, S3 and S4 are selected and S2 is not selectable, with a status naming Project B. When the user chooses Close project… and confirms, S1, S3 and S4 transfer under STO-FR-07 to paths laid out by the naming templates, and Project A reads Closing until the transfer succeeds, then Archived. S2 stays at its path. Project B's sessions and totals are unchanged. (D-W26, D-W20, D-W46, D-W80, D-W94, D-W97)
- **STO-AC-18**: Given Project A in Wrap up whose sessions hold 40 frames whose library quality is Unusable. Of the 40, 3 are in the View of open Project B, and 4 are in the Symlinks View that Closed Project D kept. When the Trash step opens, it offers "Move 37 rejected frames to Trash (size)", which includes Project D's 4. The 3 refused frames are listed as not selectable with their reason. (D-W43, D-W79, D-W80, D-W97)
- **STO-AC-19**: Given the user has approved moving the 37 frames, one frame's bytes change in place with size and mtime preserved before it moves. Another frame sits on a location where OS removal deletes immediately. When the move runs, both are refused with the reason named and left in place. The other 35 go to the OS Trash and nothing is permanently deleted. The summary names moved and refused frames, and the library marks the 35 Trashed (LIB-FR-18). (D-W43)
- **STO-AC-20**: Given a Project whose sessions include library-Unusable frames, when Wrap up's Clean up step opens, then no original frame appears in the View removal it lists. Moving rejected frames to Trash is offered only in Wrap up's Trash step, not on the Project page or in Sessions. (D-W43, D-W81, D-W97)
- **STO-AC-21**: Given a Project in Wrap up whose `Processing/` holds 118 tool files in `Processing/WBPP/` and `Processing/Siril/` and an adopted master's generated source, and whose `Output/` holds two Results. When the Trash step opens, it offers "Move 119 processing files to Trash (size)" (provisional copy): the 118 tool files plus the generated source, which is listed as a verified duplicate that names the kept library copy. The Results are not offered. After the user proceeds and confirms, the 119 go to the OS Trash and nothing is permanently deleted. (D-W70, D-W43, D-W80, D-W97, D-W98)
- **STO-AC-22**: Withdrawn (D-W97). There is no Reopen: a Closed or Archived Project is locked for good, and its archived sessions stay at their archive paths.
- **STO-AC-23**: Given the user approves "Move 3 duplicate copies to Trash (size)" for three extra copies in Captures location B, each listed with the kept copy it relies on. Before the move, one extra copy's bytes change in place with size and mtime preserved, and the kept copy of another becomes unreadable. When the move runs, then both are refused with the reason named and left in place. The third copy goes to the OS Trash after its rehash and its kept copy's re-verification both match. Its frame keeps its record, quality and memberships and lists one copy fewer. Nothing is permanently deleted, and the summary names the moved and refused copies. (D-W43, D-W74)
- **STO-AC-24**: Withdrawn (D-W94, D-W97). There is no run Trash, and Wrap up's Trash step has no Empty Trash group.
- **STO-AC-25**: Given Project A in Wrap up whose View is in Symlinks mode with 40 links, and the user ticks the View in the Clean up step. One link was replaced by a regular file and another now points to a different target. When removal runs, then PlateVault deletes the 38 links that are still the recorded symlink with the recorded target, leaves the two changed entries in place and names each with its reason, and sends nothing to the OS Trash. No original changes. (D-W81, D-W97)
- **STO-AC-26**: Given an Apply that switches Project A from Symlinks to Copies, where one old link in the View was replaced by a regular file. When the cleanup after the swap runs, then the old links that are still the recorded symlink with the recorded target are removed without following them, the regular file stays in `View (previous)/` and is named, and no original changes. Provisional: once `View (previous)/` is empty it is removed. (D-W98, D-W100)

### User Story 2 - Import (Priority: P1)

Bring frames from any card, disk or OS-mounted network folder into library storage, Lightroom style. The user picks a source, sees each file's templated destination in Captures or Calibration storage, and chooses Copy or Move. Import holds back duplicates, untyped frames and files still being written. Organized archives are added in place instead. Import replaces "File into library", and the app has no Inbox.

**Why this priority**: Import is how new captures reach the library for every later step, so it ships with the storage custody rules it depends on.

**Independent Test**: Import isolated fixture sources onto isolated Captures and Calibration locations through the running product, then compare source and destination bytes, the import summary and the library catalog.

**Acceptance Scenarios**:

- **STO-IMP-AC-01**: Given an SD card holds Ha lights of NGC 7000, flats, darks, two frames with no frame type, and one file still being written, the user picks it as an Import source. The preview then lists each light under its templated path in the chosen Captures location, such as `NGC7000/Ha/2026-04-12/light/`. Each flat and dark is listed under its per-type path in the Calibration location. The two untyped frames are listed as Unclassified and held for a type, and the growing file is listed as waiting to settle. Nothing is written before the user starts the import. (D-W11, D-W20, D-W24)
- **STO-IMP-AC-02**: Given Copy is chosen, when Import runs, then every destination is written, re-read and matches the SHA-256 of its source snapshot, and every source is unchanged. (D-W11)
- **STO-IMP-AC-03**: Given Move is chosen, when Import runs, then each source goes to the OS Trash only after its destination verifies and the source still matches its snapshot. A failed verification keeps that source and names the item. A source on a volume with no Trash, or whose OS removal deletes immediately, is kept and reported as copied with the source kept. Nothing is permanently deleted. (D-W11)
- **STO-IMP-AC-04**: Given a saved source was last imported on 2026-09-28, and since then 20 new frames were written to it and 5 earlier frames were copied back under new names. When the user runs Import new, only the 20 are imported. The summary lists the 5 as duplicates skipped by SHA-256, and no second copy is created. (D-W11, D-W24)
- **STO-IMP-AC-05**: Given an already organized archive folder, when the user chooses Add existing library folder, then it is registered and indexed in place under LIB-FR-02, and no file is copied, renamed or moved. (D-W11)
- **STO-IMP-AC-06**: Given a templated destination path holds a file with different bytes, the preview blocks that item. PlateVault never overwrites the file, and the item stays blocked until the user changes the template or leaves the item out. A file with the same bytes at that path is a skipped duplicate. Other items proceed. (D-W11, D-W24)
- **STO-IMP-AC-07**: Given two Unclassified frames in the preview, the user sets one to flat and leaves the other unset. The flat then routes to its Calibration path and imports. The summary lists the other as held Unclassified and not imported. (D-W24)
- **STO-IMP-AC-08**: Given Settings > Naming, when the user types `{target}/{date}/{filter}/` into the light template's text field, then the live preview beside it shows the sample path, and the token table lists each token with what it renders when its value is available and when it is not. Typing `{object}`, which is not a listed token, or a template containing `..` or a reserved name shows an inline error and cannot be saved. When the user sets `{filter}` to omit when unavailable, the preview for a frame without a filter leaves that segment and one adjacent `/` out instead of writing `nofilter`, so it reads `M31/2026-10-04/` with no empty folder. Restore defaults returns the per-type defaults. The next Import and Archive previews use the saved template. (D-W20, D-W84)
- **STO-IMP-AC-09**: Given a source on an OS-mounted network share, when the share is unmounted mid-import, then verified items keep their state and the source reads Offline. No source of an unverified item is trashed. When the share returns, Retry resumes the recorded work without copying verified items again and without relying on filename presence. (D-W11, D-W12)
- **STO-IMP-AC-10**: Given lights with no OBJECT and no other Target evidence, when they are previewed, then their `{target}` segment reads `unclassified` and the preview names that fallback. After import they appear in Sessions under "Needs a Target" (LIB-FR-17). (D-W20, D-W24, D-W35, D-W39)
- **STO-IMP-AC-11**: Given an SD card holds two nights of Ha lights, darks from a camera model that two rigs share, and no flats. When the preview opens, then it asks which camera alias the darks belong to. After the user picks one, the review shows each new light session's darks as pinned automatically or suggested, and its flats as not found, where the user can add flat files to this import, choose No flats or leave them for later. The import never waits: a session left for later lands in "Needs calibration" (LIB-FR-17), and no Project can add it until its calibration is settled. (D-W104, D-W105)

### Edge Cases

The [root contract](../063-clean-rebuild-contract/spec.md) governs file custody, uncertainty, exact membership, failed writes, and independent lifecycle decisions. Each acceptance scenario tests observable outcomes; no mock acknowledgment counts as terminal success.

- In Wrap up, the Trash step's moves and the Archive step's transfer run under separate confirmations, Trash first. A frame that a running archive transfer is moving is refused by Move to Trash until that transfer settles. (D-W70, D-W74, D-W80)
- When no Calibration location is registered, Import blocks only the calibration items and names the missing role; lights still import.
- Clean up, the Trash moves, Archive and Apply never overlap on one Project: provisionally, one PlateVault operation runs per Project at a time (PREP-FR-19), and Wrap up opens only once no change is pending (PRJ-FR-14).

## Requirements

### Functional Requirements

- **STO-FR-01**: Clean up removes only the entries PlateVault placed: the links and copies in the Project's View (PREP-FR-16), and whatever `View (previous)/` still holds after an Apply (STO-FR-10). Provisional: it runs only from the Clean up step of the Project's Wrap up (PRJ-FR-14), which offers removing the View, ticked for Copies and unticked for Symlinks, and lists each entry `View (previous)/` still holds, unticked, with item counts and sizes. No other place offers it; an open Project removes only the old View an Apply replaced (STO-FR-10). Clean up shows the entries in groups with counts, sizes, proposed actions and Inspect files, and a copy hard-linked into several night folders counts once. Files in `Processing/` and `Output/` are never listed, and neither are original sources or library frames. Users can toggle groups and individual entries. Selecting a group never authorizes deleting a whole directory. (D-W3, D-W81, D-W97, D-W98)
- **STO-FR-02**: Each file shows path, role, other Project references, retained-original evidence, and estimated bytes. Link sizes are never presented as guaranteed reclaim. (D-W3)
- **STO-FR-03**: Originals are protected. Library raw files are outside Clean up; rejected originals reach the OS Trash only through the Trash step of the Project's Wrap up (STO-FR-14). (D-W3, D-W26, D-W43, D-W80)
- **STO-FR-04**: Review cleanup lists exactly the selected and retained entries. Copies and every other file go to the OS Trash. The one exception is a symlink PlateVault placed: it is deleted, not trashed, because it holds no data, and only after a no-follow check that it is still the recorded symlink with its recorded target. A link that fails the check is left in place and named. Removing a View copy needs verified retained originals; removing a duplicate names the copy kept. Review records each selected entry's identity and SHA-256, a link's identity and target path without following it, and the retained original or kept copy it relies on. Execution re-verifies them immediately before each move to Trash or link deletion (D19). Trash support is shown per location with movable and blocked counts, and an OS action that deletes immediately counts as unsupported. Stale identity, drift, insufficient proof, an unavailable source, or ambiguous ownership stops the affected item. Links are never followed. (D-W81)
- **STO-FR-05**: Trash execution shows progress, per-item outcomes, and an exact complete or partial summary, and the Project records what was removed and what remains. Unsupported Trash refuses the item and offers Keep files or Reveal location. No permanent-delete fallback exists. Restoring relies on the OS Trash, with no guarantee once it is emptied. (D-W3)
- **STO-FR-06**: Archive starts from the Archive step of a Project's Wrap up (STO-FR-13). Archive review shows destination paths laid out by the naming templates (STO-IMP-FR-07), bytes, source identities, affected Projects, and reference updates. Each session row expands to its files with their from and to paths. Membership and exclusions stay fixed. It also shows destination volume identity, free space, and writability; a different volume at the same path is a conflict. Each View's current and proposed reference is shown: a symlinked entry is repointed when its session moves, with no implicit change of mode. (D-W3, D-W11, D-W20, D-W80, D-W81, D-W86)
- **STO-FR-07**: Verified transfer copies a source snapshot, writes durably and re-reads the destination to compare hashes. Retire a source only when its current identity and digest match that snapshot, the destination re-verifies and every affected reference passes immediately before retirement. Any failed check blocks the item and retains its source; source drift retains both versions for review. References report completed, blocked or uncertain. Expected and observed reclaim remain separate.
- **STO-FR-08**: If the archive is disconnected later, totals and membership are kept, inputs show Offline, and Apply refuses rather than omits them, listing them as offline originals (VSEL-FR-14). After an interruption the user sees destination-verified, source-retained, reference-updated, and pending work. Retry resumes the recorded work and never relies on filename presence. Failure sequencing follows D06 in the root decision register.
- **STO-FR-09**: Withdrawn (D-W11). "File into library" from Sessions is dropped. Import (STO-IMP-FR-01 through STO-IMP-FR-08) brings files into library storage, and "Add existing library folder" indexes organized folders in place.
- **STO-FR-10**: After Apply swaps in the new View (PREP-FR-06), this feature removes the old one from `View (previous)/`. Each old copy is deleted outright, not sent to the Trash, and only once PlateVault has verified that its original still exists and matches its recorded digest and that the copy is still what PlateVault placed. A copy it can't verify, a copy that differs from what PlateVault placed, and a file PlateVault didn't place that the user left unticked in the Apply sheet (VSEL-FR-17) stay in `View (previous)/`. Old symlinks are removed only after the no-follow check of STO-FR-04 and are never followed; a link that fails the check stays and is named. Provisional: `View (previous)/` is removed once empty; otherwise the Project shows what it still holds, with Reveal and a reviewed Move to Trash under STO-FR-04 and STO-FR-05, and Wrap up's Clean up offers it (STO-FR-01). Apply never bypasses the custody rules. (D-W98, D-W100)
- **STO-FR-11**: There is no Storage surface (P-STO2). Registered locations, their availability and their footprints show in Settings > Locations (LIB-FR-21). A Project's footprint shows on the Project and in its Apply sheet (PREP-FR-08). Library-wide content-identity duplicates show through the Sessions Duplicates filter and the session-row badge (LIB-FR-22), which open the Duplicates review. Archive transfers show as running work and in Activity. Showing a duplicate does not authorize its disposal; removal remains governed by reviewed custody scope. (D-W3, D-W86, D-W92)
- **STO-FR-12**: Destination collisions never overwrite. External drift in app-written references or operation entries is identified before mutation and blocks the affected stale item for review.
- **STO-FR-13**: This feature executes the Archive step of a Project's Wrap up (PRJ-FR-14) for the Project's sessions. A session that another Project that is not Closed holds stays at its path; the step lists it as not selectable and names that Project. Being another Project's suggestion does not count. The selected sessions transfer under STO-FR-06 through STO-FR-08 when the user confirms Close project…. The transfer runs in the background, and the Project reads Closing until it succeeds, then Archived. Archive is optional: proceeding with no session selected closes the Project with no archive, which is valid. Archiving changes no Project's sessions or totals. There is no Reopen and no restore: archived sessions stay at their archive paths. (D-W26, D-W46, D-W80, D-W94, D-W97)
- **STO-FR-14**: This feature executes the "Move N rejected frames to Trash (size)" offer of Wrap up's Trash step. Which frames the offer covers, and which it refuses with their reasons, follow PRJ-FR-15. This is the only way PlateVault moves a library frame to the Trash: it is not part of Clean up and is not offered anywhere else. A calibration master's Move to Trash (CAL-FR-17) is separate: this feature executes it under STO-FR-04 and STO-FR-05. Size is the expected reclaim and excludes bytes still held by another hard link. Besides the PRJ-FR-15 refusals, the step lists every custody refusal under STO-FR-15 with its reason. The Trash step confirms the moves the user selected in it together, and Archive is a separate step. (D-W43, D-W26, D-W70, D-W74, D-W79, D-W80, D-W82, D-W97)
- **STO-FR-15**: Moving rejected frames follows the cleanup custody rules. It acts only on copies in registered Captures locations, never on links or copies in a View, or on files outside a registered location. Every physical copy of a frame moves; if any copy is refused, the whole frame is refused. Review records each copy's identity and SHA-256, and execution re-verifies them immediately before each move (D19). An Offline or unreadable location, drift, a stale review, or a location whose OS removal deletes immediately or has no Trash refuses the frame and leaves it in place. Files go to the OS Trash only, with no permanent delete and no fallback. Execution shows progress, per-frame outcomes and an exact summary of moved and refused frames. LIB marks moved frames Trashed (LIB-FR-18). Undo is Put back in the OS Trash followed by a rescan. The same custody rules govern the two moves of STO-FR-16, with one difference for duplicates. A duplicate copy may sit in any registered location, it moves on its own, and its frame keeps the kept copy. (D-W43, D-W57, D-W70, D-W74)
- **STO-FR-16**: This feature executes the "Move N processing files to Trash (size)" (provisional copy) and "Move N duplicate copies to Trash (size)" offers of Wrap up's Trash step. Which items each offer covers, keeps, refuses and counts in N follow PRJ-FR-15. Files in `Output/` (RES-FR-06), adopted masters and candidate masters (CAL-FR-06) stay protected, and the step names a candidate master so the user can adopt it first. An adopted master's generated source moves under the same approval as the other `Processing/` files, as a verified duplicate that names the kept library copy (STO-FR-04), and execution re-verifies that copy before moving the source. For each duplicate copy, review records the copy's identity and SHA-256 and names the kept copy it relies on. Execution rehashes the copy and re-verifies the kept copy immediately before the move (D19). A copy whose bytes no longer match, or whose kept copy cannot be re-verified, is refused and left in place. A moved copy leaves its frame's list of physical copies (LIB-FR-08); the frame keeps its record, quality decisions and memberships. Review records each other item's identity and SHA-256, and execution re-verifies it immediately before each move (D19). Besides the PRJ-FR-15 refusals, the step lists every custody refusal of STO-FR-15 with its reason. Files go to the OS Trash only, with no permanent delete. The Trash step confirms the moves the user selected in it together, and Archive is a separate step. (D-W70, D-W43, D-W74, D-W80, D-W97, D-W98)
- **STO-FR-17**: Withdrawn (D-W94, D-W97). There is no run Trash, so there is no Empty Trash, and Wrap up's Trash step has no Empty Trash group.
- **STO-IMP-FR-01**: Import has its own workflow entry in main navigation and on Home. A source is any local folder, removable volume, or network path the OS has already mounted; PlateVault mounts nothing (LIB-FR-19). A source can be saved under a name. Import new on a saved source offers only files not already imported: a file whose SHA-256 matches a frame imported from that source or any indexed frame is skipped. "Add existing library folder" sits beside Import and registers an organized folder to index in place (LIB-FR-02), with no copy. Import replaces "File into library", and the app has no Inbox. Archive is unchanged and stays separate (STO-FR-06). (D-W11, D-W7, D-W12)
- **STO-IMP-FR-02**: Import classifies each source file by its frame-type header. Lights route to a Captures location. Darks, flats, bias frames and masters route to a Calibration location. A file with no frame type is Unclassified: it is held in the preview until the user sets a type, and it is never imported untyped. A file whose SHA-256 matches an indexed frame or another file in the same import is skipped as a duplicate and listed, and only the first copy is imported. A file whose size or modification time is still changing is held as waiting to settle and is offered once both stay unchanged across consecutive checks. When a role has several locations, the user chooses one for the import; when a role has none, its items are blocked with the missing role named and a way to register one (LIB-FR-01). (D-W24)
- **STO-IMP-FR-03**: Before anything is written, the preview lists every source file with its templated destination path, and counts and bytes per destination. It also lists duplicates, Unclassified and waiting-to-settle files, collisions, and each destination volume's free space and writability. The preview may name a light's confirmed rig. If the light's FILTER value then matches no filter on that rig, the preview shows the value as unknown with the "Add {value} to {rig}" prompt of PLAN-EQ-FR-04, and the prompt holds nothing back. When the rigs hold two or more cameras of a dark's or bias's model, the preview asks which camera alias it belongs to (LIB-FR-26). The review shows each new light session's darks, flats and bias as pinned automatically, suggested or not found, and Import never waits for calibration (LIB-FR-24). The user chooses Copy or Move for the whole import. Starting the import approves only the displayed items and records each source's identity and SHA-256. (D-W11, D-W20, D-W24, D-W31, D-W104, D-W105)
- **STO-IMP-FR-04**: Copy uses verified transfer (STO-FR-07): it copies a source snapshot, writes durably, re-reads the destination and compares SHA-256, and leaves the source untouched. Move does the same, then re-verifies the source against its snapshot immediately before sending it to the OS Trash (D19). A failed destination verification keeps the source; source drift keeps both versions for review. If the source volume has no Trash or its OS removal deletes immediately, the source is kept and the item reports copied, source kept. Import never permanently deletes and never overwrites. (D-W11)
- **STO-IMP-FR-05**: A destination path that holds a file with different bytes blocks the item until the user changes the template or leaves the item out (STO-FR-12). A file with identical bytes at that path is a duplicate and is skipped. Templates set the folder path; files keep their original basenames. (D-W11, D-W24)
- **STO-IMP-FR-06**: Import shows per-item progress and outcomes and an exact summary. The summary counts imported items, skipped duplicates, held Unclassified and waiting-to-settle files, blocked items, failed verifications, and Move sources trashed or kept, and is recorded in Activity. Hashing a network source shows progress and resumes after an interruption (LIB-FR-19). After an interruption or an unmounted source or destination, verified items keep their state and the rest stay pending. Retry resumes the recorded work after revalidating identities and never relies on filename presence. (D-W11, D-W12)
- **STO-IMP-FR-07**: Naming templates are used by Import and Archive and return from the legacy app, with three changes. The legacy "Auto-apply pattern" checkbox and the generic project folder pattern are dropped, because the Project folder and its View layout are fixed (PREP-FR-06, PREP-FR-16), and the chip editor is replaced by plain text templates. Nine tokens resolve from frame metadata, each with a fallback: `{target}` → `unclassified`, `{filter}` → `nofilter`, `{date}` → `undated` (ISO observing-night local date), `{frame_type}` → `unknown` (lowercase), `{camera}` → `unknown-camera`, `{exposure}` → `unknown-exposure`, `{gain}` → `unknown-gain`, `{binning}` → `1x1`, `{set_temp}` → `untempered`. Per-type defaults are light `{target}/{filter}/{date}/light/`, flat `flats/{filter}/{date}/`, dark `darks/{exposure}/`, bias `bias/`, master flat `masters/flats/{filter}/`, master dark `masters/darks/{exposure}/` and master bias `masters/bias/`. Only overridden types are stored. Settings > Naming is one page with a text field per frame type, a live preview beside each field that resolves it against sample metadata, and a table of the available tokens. The table shows each token's rendering when its value is available and when it is not, and lets the user set a token to be left out when its value is unavailable instead of writing its fallback. A left-out token also takes one adjacent separator with it: the separator before it, or the one after it when nothing precedes it. So without a filter, `{target}_{filter}_{date}` resolves to `M31_2026-10-04` and `{target}/{filter}/{date}/` to `M31/2026-10-04/`. A template may hold only the listed tokens, literals and the separators `/`, `-`, `_` and space. Validation runs as the user types and again when the template is saved or resolved, and shows errors inline. Resolution sanitizes names, rejects path traversal and reserved names, and caps lengths. Restore defaults is available. The preview names every fallback token it used. (D-W20, D-W58, D-W84, D-W98)
- **STO-IMP-FR-08**: Imported files are indexed as they land under LIB-FR-16. Lights appear in Sessions and calibration frames in the Calibration library. Import changes no quality decision, Target or equipment association. (D-W24)
