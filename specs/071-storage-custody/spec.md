## User Scenarios & Testing

### User Story 1 - Storage operations: View Clean up, verified archive and Wrap up Trash (Priority: P1)

Selectable Clean up of a Project's View to the OS Trash with retained-original proof, the removal of the old View after each Apply, and verified archive transfers that repoint affected View entries and never retire a source before verification. When a Project is wrapped up, this feature executes the custody steps of its Wrap up, which PV-PRJ owns. Its Clean up step removes the View and, provisionally, whatever `View (previous)/` still holds. Its Trash step moves the Project's rejected frames, `Processing/` files and duplicate copies to the OS Trash, and its Archive step transfers the sessions no other open Project holds. A Closed or Archived Project is locked for good, so nothing here changes it or restores its sessions, and, provisionally, it has no Reopen (D-W97).

**Why this priority**: This feature owns the workflow steps listed below without imposing unrelated product features.

**Independent Test**: Exercise the acceptance scenarios through the running product with isolated inputs. Existing baseline code does not prove the redesigned behavior.

### User Story 2 - Import (Priority: P1)

Bring frames from any card, disk or OS-mounted network folder into library storage, Lightroom style. The user picks a source, sees each file's templated destination in Captures or Calibration storage, and chooses Copy or Move. Import holds back duplicates, untyped frames and files still being written. Organized archives are added in place instead. Import replaces "File into library", and the app has no Inbox.

**Why this priority**: Import is how new captures reach the library for every later step, so it ships with the storage custody rules it depends on.

**Independent Test**: Import isolated fixture sources onto isolated Captures and Calibration locations through the running product, then compare source and destination bytes, the import summary and the library catalog.

**Acceptance Scenarios**:

- **STO-IMP-AC-01**: Given an SD card holds Ha lights of NGC 7000, flats, darks, two frames with no frame type, and one file still being written, the user picks it as an Import source. The preview then lists each light under its templated path in the chosen Captures location, such as `NGC7000/Ha/2026-04-12/light/`. Each flat and dark is listed under its per-type path in the Calibration location. The two untyped frames are listed as Unclassified and held for a type, and the growing file is listed as waiting to settle. Nothing is written before the user starts the import. (D-W11, D-W20, D-W24)
- **STO-IMP-AC-02**: Given Copy is chosen, when Import runs, then every destination is written, re-read and matches the SHA-256 of its source snapshot, and every source is unchanged. (D-W11)
- **STO-IMP-AC-03**: Given Move is chosen, when Import runs, then each source goes to the OS Trash only after its destination verifies and the source still matches its snapshot. A failed verification keeps that source and names the item. A source on a volume with no Trash, or whose OS removal deletes immediately, is kept and reported as copied with the source kept. Nothing is permanently deleted. (D-W11)
- **STO-IMP-AC-04**: Given a saved source was last imported on 2026-09-28, and since then 20 new frames were written to it and 5 earlier frames were copied back under new names. When the user runs Import new, only the 20 are imported. The summary lists the 5 as duplicates skipped by SHA-256, and no second copy is created. (D-W11, D-W24)
- **STO-IMP-AC-05**: Given an already organized archive folder, when the user chooses Add existing library folder, then it is registered and indexed in place under LIB-FR-02, and no file is copied, renamed or moved. (D-W11)
- **STO-IMP-AC-06**: Given a templated destination path holds a file with different bytes, the preview blocks that item. PlateVault never overwrites the file, and the item stays blocked until the user changes the template or leaves the item out. A file with the same bytes at that path is a skipped duplicate. Other items proceed. (D-W11, D-W24)
- **STO-IMP-AC-07**: Given two Unclassified frames in the preview, the user sets one to flat and leaves the other unset. The flat then routes to its Calibration path and imports. The summary lists the other as held Unclassified and not imported. (D-W24)
- **STO-IMP-AC-08**: Given Settings > Naming, when the user types `{target}/{date}/{filter}/` into the light template's text field, then the live preview beside it shows the sample path, and the token table lists each token with what it renders when its value is available and when it is not. Typing `{object}`, which is not a listed token, or a template containing `..` or a reserved name shows an inline error and cannot be saved. When the user sets `{filter}` to omit when unavailable, the preview for a frame without a filter leaves that segment and one adjacent `/` out instead of writing `nofilter`, so it reads `M31/2026-10-04/` with no empty folder. Restore defaults returns the per-type defaults. The next Import and Archive previews use the saved template. (D-W20, D-W84)
- **STO-IMP-AC-09**: Given a source on an OS-mounted network share, when the share is unmounted mid-import, then the import reads Interrupted, verified items keep their state and the source reads Offline. No source of an unverified item is trashed. When the share returns, Retry resumes the recorded work without copying verified items again and without relying on filename presence. (D-W11, D-W12, D-W154)
- **STO-IMP-AC-13**: Given an import from the SD card `Card-1`, when the card is pulled mid-import, then the import reads Interrupted, and every source of an unverified item stays in place. After the card is inserted again, Retry resumes the import and copies no verified item again. (D-W154)
- **STO-IMP-AC-10**: Given lights with no OBJECT and no other Target evidence, when they are previewed, then their `{target}` segment reads `unclassified` and the preview names that fallback. After import they appear in Sessions under "Needs a Target" (LIB-FR-17). (D-W20, D-W24, D-W35, D-W39)
- **STO-IMP-AC-11**: Given an SD card holds two nights of Ha lights, darks from a camera model that two rigs share, and no flats. When the preview opens, then it asks which camera alias the darks belong to. After the user picks one, the review shows each new light session's darks as pinned automatically or suggested, and its flats as not found, where the user can add flat files to this import, choose No flats or leave them for later. The import never waits: a session left for later lands in "Needs calibration" (LIB-FR-17), and no Project can add it until its calibration is settled. (D-W104, D-W105)
- **STO-IMP-AC-12**: Given Settings > Naming, then its Group keywords section has a row for Group reading GROUP and a row for Mosaic panel reading PANEL, each with its own Edit…. When the user edits Mosaic panel to `MOSAIC_PANEL`, then saving is refused under the field with a reason naming WBPP. `MOSAIC-PANEL` saves. `SET-GROUP` and `NIGHT-SET` are refused, because WBPP would read GROUP or NIGHT inside them at the hyphen. Settings > Applications has no keyword row. (D-W146)

### Edge Cases

The [root contract](../063-clean-rebuild-contract/spec.md) governs file custody, uncertainty, exact membership, failed writes, and independent lifecycle decisions. Each acceptance scenario tests observable outcomes; no mock acknowledgment counts as terminal success.

- In Wrap up, the Trash step's moves and the Archive step's transfer run under separate confirmations, Trash first. A frame that a running archive transfer is moving is refused by Move to Trash until that transfer settles. (D-W70, D-W74, D-W80)
- When no Calibration location is registered, Import blocks only the calibration items and names the missing role; lights still import.
- Clean up, the Trash moves, Archive and Apply never overlap on one Project: provisionally, one PlateVault operation runs per Project at a time (PREP-FR-19), and Wrap up opens only once no change is pending (PRJ-FR-14).

## Requirements

### Functional Requirements

- **STO-FR-01**: Clean up lists the links and copies PlateVault placed in the Project's View (PREP-FR-16) and offers removing the View, ticked for Copies and unticked for Symlinks (D-W81). Provisional: it also lists whatever `View (previous)/` still holds after an Apply (STO-FR-10), including files PlateVault didn't place, each unticked, with item counts and sizes. Provisional: it runs only from the Clean up step of the Project's Wrap up (PRJ-FR-14). No other place offers it; an open Project removes only the old View an Apply replaced (STO-FR-10). Clean up shows the entries in groups with counts, sizes, proposed actions and Inspect files. Each copy is an independent file and counts on its own, also when the same flat set sits in several night folders (PREP-FR-04). Files in `Processing/` and `Output/` are never listed, and neither are original sources or library frames. Users can toggle groups and individual entries. Selecting a group never authorizes deleting a whole directory. (D-W3, D-W81, D-W97, D-W98)
- **STO-FR-02**: Each file shows path, role, other Project references, retained-original evidence, and estimated bytes. Link sizes are never presented as guaranteed reclaim. (D-W3)
- **STO-FR-03**: Originals are protected. Library raw files are outside Clean up. Rejected originals reach the OS Trash only through the Trash step of the Project's Wrap up (STO-FR-14) or the library's Unusable clean-up (STO-FR-18). (D-W3, D-W26, D-W43, D-W80, D-W156)
- **STO-FR-04**: Review cleanup lists exactly the selected and retained entries. Copies and every other file go to the OS Trash. The one exception is a symlink PlateVault placed: it is deleted, not trashed, because it holds no data, and only after a no-follow check that it is still the recorded symlink with its recorded target. A link that fails the check is left in place and named. Removing a View copy needs verified retained originals; removing a duplicate names the copy kept. Review records each selected entry's identity and SHA-256, a link's identity and target path without following it, and the retained original or kept copy it relies on. Execution re-verifies them immediately before each move to Trash or link deletion (D19). Trash support is shown per location with movable and blocked counts, and an OS action that deletes immediately counts as unsupported. Stale identity, drift, insufficient proof, an unavailable source, or ambiguous ownership stops the affected item. Links are never followed. (D-W81)
- **STO-FR-05**: Trash execution shows progress, per-item outcomes, and an exact complete or partial summary, and the Project records what was removed and what remains. Unsupported Trash refuses the item and offers Keep files or Reveal location. No permanent-delete fallback exists. Restoring relies on the OS Trash, with no guarantee once it is emptied. (D-W3)
- **STO-FR-06**: Archive starts from the Archive step of a Project's Wrap up or from Sessions (LIB-FR-17), under the same rule (STO-FR-13). Archive review shows destination paths laid out by the naming templates (STO-IMP-FR-07), bytes, source identities, affected Projects, and reference updates. Each session row expands to its files with their from and to paths. Membership and exclusions stay fixed. It also shows destination volume identity, free space, and writability; a different volume at the same path is a conflict. Each View's current and proposed reference is shown: a symlinked entry is repointed when its session moves, with no implicit change of mode. That includes the View a Closed or Archived Project kept: Archive repoints its symlinks and records the repoint in Activity, and the Project's sessions, goals, snapshot and Wrap up record stay unchanged. Provisional: each repoint also records the link's new target with the archive copy's SHA-256, which the transfer verified. Open re-verifies the link against that record (PREP-FR-10), so a repointed View still opens and doesn't read as drift. (D-W3, D-W11, D-W20, D-W80, D-W81, D-W86, D-W111, D-W120)
- **STO-FR-07**: Verified transfer copies a source snapshot, writes durably and re-reads the destination to compare hashes. Retire a source only when its current identity and digest match that snapshot, the destination re-verifies and every affected reference passes immediately before retirement. Any failed check blocks the item and retains its source; source drift retains both versions for review. References report completed, blocked or uncertain. Expected and observed reclaim remain separate.
- **STO-FR-08**: If the archive is disconnected later, totals and membership are kept, inputs show Offline, and Apply refuses rather than omits them, listing them as offline originals (VSEL-FR-14). After an interruption the user sees destination-verified, source-retained, reference-updated, and pending work. Retry resumes the recorded work and never relies on filename presence. Failure sequencing follows D06 in the root decision register.
- **STO-FR-09**: Withdrawn (D-W11). "File into library" from Sessions is dropped. Import (STO-IMP-FR-01 through STO-IMP-FR-08) brings files into library storage, and "Add existing library folder" indexes organized folders in place.
- **STO-FR-10**: After Apply swaps in the new View (PREP-FR-06), this feature removes the old one from `View (previous)/`. Each old copy is deleted outright, not sent to the Trash, and only once PlateVault has verified that its original still exists and matches its recorded digest and that the copy is still what PlateVault placed. A copy it can't verify, a copy that differs from what PlateVault placed, and a file PlateVault didn't place that the user left unticked in the Apply sheet (VSEL-FR-20) stay in `View (previous)/`. Old symlinks are removed only after the no-follow check of STO-FR-04 and are never followed; a link that fails the check stays and is named. The Project shows what `View (previous)/` still holds, and Wrap up's Clean up offers it (STO-FR-01). At the next Apply, Apply waits until the user has reviewed each file there: keep it, move it elsewhere, or move it to the OS Trash under STO-FR-04 and STO-FR-05 (VSEL-FR-14). `View (previous)/` has no numbered generations. A file the user keeps isn't asked about again, keeps its bytes and is never deleted. A kept file that has gone from disk before Apply is reported as missing, never skipped silently (D-W137; owner's answer, 2026-10-20). Provisional: `View (previous)/` is removed once empty. On the next Apply, kept files move to a separate kept folder; a `-2` suffix is added on name clashes. Apply never bypasses the custody rules. (D-W98, D-W100, D-W110; owner's answer, 2026-10-19, astro-plan-rzbzu.1)
- **STO-FR-11**: There is no Storage surface (P-STO2). Registered locations, their availability and their footprints show in Settings > Locations (LIB-FR-21). A Project's footprint shows on the Project and in its Apply sheet (PREP-FR-08). Library-wide content-identity duplicates show through the Sessions Duplicates filter and the session-row badge (LIB-FR-22), which open the Duplicates review. Archive transfers show as running work and in Activity. Showing a duplicate does not authorize its disposal; removal remains governed by reviewed custody scope. (D-W3, D-W86, D-W92)
- **STO-FR-12**: Destination collisions never overwrite. On a volume without an atomic no-replace rename, such as exFAT, a folder moves over its own empty placeholder, and a file moves as a verified copy (D-W139; owner's answer, 2026-10-20). PlateVault knows its own unregistered copy at a master's adoption destination by its recorded operation entry and digest. Adoption's refusal names that copy and offers a reviewed Move to Trash under STO-FR-04 and STO-FR-05, and adoption then retries (CAL-FR-07). External drift in app-written references or operation entries is identified before mutation and blocks the affected stale item for review. (D-W119)
- **STO-FR-13**: This feature executes the Archive step of a Project's Wrap up (PRJ-FR-14) for the Project's sessions. A session that another open Project holds stays at its path; the step lists it as not selectable and names that Project. A Closed or Archived Project doesn't keep a session: its sessions can be archived, and Archive repoints its kept View (STO-FR-06). Being another Project's suggestion does not count. The selected sessions transfer under STO-FR-06 through STO-FR-08 when the user confirms Close project…. The transfer runs in the background, and the Project reads Closing until it succeeds, then Archived. Archive is optional: proceeding with no session selected closes the Project with no archive, which is valid. Archiving changes no Project's sessions or totals. There is no restore: archived sessions stay at their archive paths. Provisional: there is no Reopen. Sessions > Archive… (LIB-FR-17) follows the same rule for the sessions the user selects there; it has no Stop action. A session that an open Project holds can't be selected, and its row names that Project. A session that only Closed or Archived Projects hold is archived, and their kept Views are repointed (STO-FR-06). Being a Project's suggestion doesn't count. The transfer runs under STO-FR-06 through STO-FR-08 when the user approves Archive, and it closes no Project and changes none. (D-W26, D-W46, D-W80, D-W94, D-W97, D-W120; owner's answer, 2026-10-19, astro-plan-rzbzu.1)
- **STO-FR-14**: This feature executes the "Move N rejected frames to Trash (size)" offer of Wrap up's Trash step. Which frames the offer covers, and which it refuses with their reasons, follow PRJ-FR-15. Besides this offer, two other routes move a library frame or a duplicate copy to the Trash: Wrap up's "Move N duplicate copies to Trash (size)" offer (STO-FR-16) and the library clean-ups of STO-FR-18 (D-W156). None of them is part of Clean up. A calibration master's Move to Trash (CAL-FR-17) is separate: this feature executes it under STO-FR-04 and STO-FR-05. Size is the expected reclaim and excludes bytes still held by another hard link. Besides the PRJ-FR-15 refusals, the step lists every custody refusal under STO-FR-15 with its reason. The Trash step confirms the moves the user selected in it together, and Archive is a separate step. (D-W43, D-W26, D-W70, D-W74, D-W79, D-W80, D-W82, D-W97, D-W156)
- **STO-FR-15**: Moving rejected frames follows the cleanup custody rules. It acts only on copies in registered Captures locations, never on links or copies in a View, or on files outside a registered location. Every physical copy of a frame moves; if any copy is refused, the whole frame is refused. Review records each copy's identity and SHA-256, and execution re-verifies them immediately before each move (D19). An Offline or unreadable location, drift, a stale review, or a location whose OS removal deletes immediately or has no Trash refuses the frame and leaves it in place. Files go to the OS Trash only, with no permanent delete and no fallback. Execution shows progress, per-frame outcomes and an exact summary of moved and refused frames. LIB marks moved frames Trashed (LIB-FR-18). Undo is Put back in the OS Trash followed by a rescan. The same custody rules govern the two moves of STO-FR-16, with one difference for duplicates. A duplicate copy may sit in any registered location, it moves on its own, and its frame keeps the kept copy. (D-W43, D-W57, D-W70, D-W74)
- **STO-FR-16**: This feature executes the "Move N processing files to Trash (size)" (provisional copy) and "Move N duplicate copies to Trash (size)" offers of Wrap up's Trash step. Which items each offer covers, keeps, refuses and counts in N follow PRJ-FR-15. Files in `Output/` (RES-FR-06), adopted masters and candidate masters (CAL-FR-06) stay protected, and the step names a candidate master so the user can adopt it first. An adopted master's generated source moves under the same approval as the other `Processing/` files, as a verified duplicate that names the kept library copy (STO-FR-04), and execution re-verifies that copy before moving the source. When copies tie for the kept copy because they sit in the same location, the copy PlateVault catalogued first is preselected, and nothing is removed without review. For each duplicate copy, review records the copy's identity and SHA-256 and names the kept copy it relies on. Execution rehashes the copy and re-verifies the kept copy immediately before the move (D19). A copy whose bytes no longer match, or whose kept copy cannot be re-verified, is refused and left in place. A moved copy leaves its frame's list of physical copies (LIB-FR-08); the frame keeps its record, quality decisions and memberships. Review records each other item's identity and SHA-256, and execution re-verifies it immediately before each move (D19). Besides the PRJ-FR-15 refusals, the step lists every custody refusal of STO-FR-15 with its reason. Files go to the OS Trash only, with no permanent delete. The Trash step confirms the moves the user selected in it together, and Archive is a separate step. (D-W70, D-W43, D-W74, D-W80, D-W97, D-W98, D-W116)
- **STO-FR-17**: Withdrawn (D-W94, D-W97). There is no run Trash, so there is no Empty Trash, and Wrap up's Trash step has no Empty Trash group.
- **STO-FR-18**: Two library clean-ups trash library files outside any Project (D-W156). The Unusable clean-up offers "Move N Unusable frames to Trash (size)" for library-Unusable frames. It refuses a frame that the View of an open Project links or copies, and a calibration frame pinned on a session, and lists each refused frame with its reason. A Closed or Archived Project's kept View doesn't block a frame, as in Wrap up (STO-FR-13). The duplicates clean-up in the Sessions › Duplicates review (LIB-FR-22) lists groups of byte-identical copies, with the kept copy preselected by the keeper rule of PRJ-FR-15. It moves the other copies the user confirms and refuses an extra copy that the View of an open Project links or copies. Both follow the custody rules of STO-FR-15: the user confirms a reviewed list, files go to the OS Trash only, and LIB marks moved frames Trashed (LIB-FR-18).
- **STO-IMP-FR-01**: Import has its own workflow entry in main navigation and on Home. A source is any local folder, removable volume, or network path the OS has already mounted; PlateVault mounts nothing (LIB-FR-19). A source can be saved under a name. Import new on a saved source offers only files not already imported: a file whose SHA-256 matches a frame imported from that source or any indexed frame is skipped. "Add existing library folder" sits beside Import and registers an organized folder to index in place (LIB-FR-02), with no copy. Import replaces "File into library", and the app has no Inbox. Archive is unchanged and stays separate (STO-FR-06). (D-W11, D-W7, D-W12)
- **STO-IMP-FR-02**: Import classifies each source file by its frame-type header. Lights route to a Captures location. Darks, flats, bias frames and masters route to a Calibration location. A file with no frame type is Unclassified: it is held in the preview until the user sets a type, and it is never imported untyped. A file whose SHA-256 matches an indexed frame or another file in the same import is skipped as a duplicate and listed, and only the first copy is imported. A file whose size or modification time is still changing is held as waiting to settle and is offered once both stay unchanged across consecutive checks. When a role has several locations, the user chooses one for the import; when a role has none, its items are blocked with the missing role named and a way to register one (LIB-FR-01). (D-W24)
- **STO-IMP-FR-03**: Before anything is written, the preview lists every source file with its templated destination path, and counts and bytes per destination. It also lists duplicates, Unclassified and waiting-to-settle files, collisions, and each destination volume's free space and writability. The preview may name a light's confirmed rig. If the light's FILTER value then matches no filter on that rig, the preview shows the value as unknown with the "Add {value} to {rig}" prompt of PLAN-EQ-FR-04, and the prompt holds nothing back. A session with no pointing or no matching Target has Unclassified preselected, so Import is available; a Target is chosen only to file the session under it (owner's answer, 2026-10-19, astro-plan-rzbzu.1). When pointing matches several Targets, Unclassified stays preselected and the preview recommends the Target nearest the field centre (D-W133; owner's answer, 2026-10-20). When the rigs hold two or more cameras of a dark's or bias's model, the preview asks which camera alias it belongs to (LIB-FR-26). The review shows each new light session as intake split it by framing, and the user can merge or re-split sessions before starting the import (LIB-FR-04, LIB-FR-24). It shows each new light session's darks, flats and bias as pinned automatically, suggested or not found, and Import never waits for calibration (LIB-FR-24). The user chooses Copy or Move for the whole import. Starting the import approves only the displayed items and records each source's identity and SHA-256. (D-W11, D-W20, D-W24, D-W31, D-W104, D-W105, D-W107)
- **STO-IMP-FR-04**: Copy uses verified transfer (STO-FR-07): it copies a source snapshot, writes durably, re-reads the destination and compares SHA-256, and leaves the source untouched. Move does the same, then re-verifies the source against its snapshot immediately before sending it to the OS Trash (D19). A failed destination verification keeps the source; source drift keeps both versions for review. If the source volume has no Trash or its OS removal deletes immediately, the source is kept and the item reports copied, source kept. Import never permanently deletes and never overwrites. (D-W11)
- **STO-IMP-FR-05**: A destination path that holds a file with different bytes blocks the item until the user changes the template or leaves the item out (STO-FR-12). A file with identical bytes at that path is a duplicate and is skipped. Templates set the folder path; files keep their original basenames. (D-W11, D-W24)
- **STO-IMP-FR-06**: Import shows per-item progress and outcomes and an exact summary. The summary counts imported items, skipped duplicates, held Unclassified and waiting-to-settle files, blocked items, failed verifications, and Move sources trashed or kept, and is recorded in Activity. Hashing a network source shows progress and resumes after an interruption (LIB-FR-19). After an interruption or an unmounted source or destination, verified items keep their state and the rest stay pending. When the source goes away mid-import, such as a pulled SD card or a dropped share, the import pauses and reads Interrupted. Reconnecting the source and choosing Retry resumes it (D-W154). Retry resumes the recorded work after revalidating identities and never relies on filename presence. (D-W11, D-W12, D-W154)
- **STO-IMP-FR-07**: Naming templates are used by Import and Archive and return from the legacy app, with three changes. The legacy "Auto-apply pattern" checkbox and the generic project folder pattern are dropped, because the Project folder and its View layout are fixed (PREP-FR-06, PREP-FR-16), and the chip editor is replaced by plain text templates. Nine tokens resolve from frame metadata, each with a fallback: `{target}` → `unclassified`, `{filter}` → `nofilter`, `{date}` → `undated` (ISO observing-night local date), `{frame_type}` → `unknown` (lowercase), `{camera}` → `unknown-camera`, `{exposure}` → `unknown-exposure`, `{gain}` → `unknown-gain`, `{binning}` → `1x1`, `{set_temp}` → `untempered`. Per-type defaults are light `{target}/{filter}/{date}/light/`, flat `flats/{filter}/{date}/`, dark `darks/{exposure}/`, bias `bias/`, master flat `masters/flats/{filter}/`, master dark `masters/darks/{exposure}/` and master bias `masters/bias/`. Only overridden types are stored. Settings > Naming is one page with a text field per frame type, a live preview beside each field that resolves it against sample metadata, and a table of the available tokens. The table shows each token's rendering when its value is available and when it is not, and lets the user set a token to be left out when its value is unavailable instead of writing its fallback. A left-out token also takes one adjacent separator with it: the separator before it, or the one after it when nothing precedes it. So without a filter, `{target}_{filter}_{date}` resolves to `M31_2026-10-04` and `{target}/{filter}/{date}/` to `M31/2026-10-04/`. A template may hold only the listed tokens, literals and the separators `/`, `-`, `_` and space. Validation runs as the user types and again when the template is saved or resolved, and shows errors inline. Resolution sanitizes names, rejects path traversal and reserved names, and caps lengths. Restore defaults is available. The preview names every fallback token it used. (D-W20, D-W58, D-W84, D-W98)
- **STO-IMP-FR-08**: Imported files are indexed as they land under LIB-FR-16. Lights appear in Sessions and calibration frames in the Calibration library. Import changes no quality decision, Target or equipment association. (D-W24)
- **STO-IMP-FR-09**: Settings > Naming also holds Group keywords: one row per grouping keyword, Group (GROUP by default) and Mosaic panel (PANEL by default), each with its own Edit…; Settings > Applications has no keyword row or dialog. A keyword name starts with a letter and may then contain letters, digits and `-`, but not `_`, because WBPP's keyword field keeps only letters, digits and `-` (PJSR commit 76e4f38c, `BPP-GUI.js` L420-L425). WBPP finds a keyword by matching it literally after any non-alphanumeric character (`BPP-Helper.js` L1109-L1130). So PlateVault also refuses a name that reads inside another keyword at a hyphen, the View keywords NIGHT, GAIN and OFFSET included. A refusal shows under the field. A Project can override both names under the same rules (PRJ-FR-28). (D-W95, D-W146)
