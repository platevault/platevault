# Application handoff research

## Decision

Store located applications, per-View handoff settings, preparation reviews, preparation revisions, their item journal, preparation operations and launch records as Tier 1 records in the clean library catalog, `crates/persistence/library`, through its single serialized writer. Evaluate profile capability evidence and plan each review in pure `platevault_core` modules. Materialize entries in a core module that writes only below the reviewed View folder, removes nothing and reads sources only through the catalog's contained no-follow reader. Launch without a shell, from the located path. The isolated rebuilt shell exposes `prep_*` commands. No legacy profile, prepared-view, launch or plan-executor code is booted or imported.

## Cross-spec seams

The six sibling plans run in parallel. Each seam states the interface PREP needs and the default PREP implements. The 066, 068, 070 and 071 planners confirmed the shapes below during planning; their own contracts govern if they change. PREP lands after 066 and 068, and 070 and 071 consume PREP. The integration task adapts to a changed shape without widening PREP behavior.

- **Cross-spec seam S1, VSEL (066) View revision.** PREP reads `Catalog::view_revision(viewId, revision)`: View ID, revision, name, optional Project, saved criteria (never browsing filters), session choices with reasons, and members. A member is one logical capture (D16) with state included or excluded, a reason and its copies, each an `ExpectedAsset`. Committed revisions are immutable, so PREP compares the requested revision with the View's current revision itself. Unresolved is not stored: an included member with no Available copy is unresolved, and PREP derives it the same way. Default: PREP reviews only a committed revision and never reads or changes a draft. A missing View or revision is NotFound.
- **Cross-spec seam S2, VSEL handoff settings.** VSEL-FR-02 gives the View an optional profile. PREP owns the per-View handoff settings record (application, input mode, link type, View location and output override) keyed by View ID. VSEL reads that record and stores no profile of its own.
- **Cross-spec seam S3, CAL (068) calibration handoff.** PREP reads `Catalog::calibration_handoff(viewId, viewRevision)`, which is read-only and starts no rehash. It holds `ready`, one assignment per light session and kind (bias, dark or flat; raw set or master), each with resolution accepted or exception, criteria verdicts, the exception reason and its input files, plus unresolved needs with reasons. An input file names an asset or an adopted master, its location ID, relative path and a fingerprint whose `contentSha256` is the accepted basis. Default: accepted and exception assignments enter the handoff, suggestions never do, and each unresolved need is a blocked item (R17). Excluding a session is a VSEL exclusion. PREP writes no calibration record.
- **Cross-spec seam S4, RES (070) operations and lifecycle.** Mark Complete calls RES's `running_view_operations(conn, viewId)` inside its completion transaction, which reads PREP's in-transaction `running_preparations(conn, viewId)`. That answer covers Running prepare and retry operations only, because open verification mutates nothing (RES-FR-07, D09). RES provides `require_view_open(conn, viewId)`, which PREP's preparation-start and Retry transactions call once 070 lands; until then no View is Complete. Open and Reveal never call it (R24).
- **Cross-spec seam S5, RES products and outputs.** `Catalog::latest_preparation(viewId)` carries the output location with folder identity for result discovery. The profile manifest carries `productInput` and `recognizedOutput` classes, unknown by default. Default: a member that is not a library asset, such as a product input, is a blocked item named unsupported, and no output is recognized.
- **Cross-spec seam S6, STO (071) prepared entries.** STO reads every entry of a preparation revision: entry ID, role, kind, path, the no-follow `ObservationFingerprint` (file ID, size and `modifiedNs`), link target, source reference, source SHA-256 basis and entry SHA-256, plus the View and output folders and the revision's `supersededBy`. PREP exposes the pure `render_handoff_file`, so STO can rewrite a handoff list under its own verified write. PREP never removes, trashes or rewrites any entry or leftover. Removal and reference repair are STO rows keyed by entry ID (PREP-FR-11, STO-FR-10). 071 extends Open verification through `Catalog::entry_custody`: a removed entry blocks Open, and a repaired target is accepted only as STO recorded it. Until 071 lands, no entry has custody rows.
- **Cross-spec seam S7, LIB (064) contained source reader.** PREP needs the catalog's no-follow containment for reads and no new library behavior. Default: the catalog crate exports a narrow reader over its existing `open_contained` checks. It takes a location ID, relative path and fingerprint, so library assets and CAL masters verify the same way (R18). No SQL moves.
- PRJ (065) has no direct seam. A Project-owned View reaches PREP only through S1.

## Resolved ambiguities

Each entry records the decision, its basis and the alternative considered. Where the spec is silent, the default follows the root [decision register](../063-clean-rebuild-contract/decisions.md).

- **R1 Storage.** PREP tables live in `crates/persistence/library/src/preparations.sql`, with SQL in `src/preparations.rs`. Basis: one serialized writer, and review, start and finalize read assets, locations, View membership and calibration in one snapshot with foreign keys. Alternative: a separate persistence crate needs a second writer connection or public library internals.
- **R2 Schema order.** The dependency order is 064 (version 6), 065 (planned version 7), 066, 068, then 069. PREP sets `SCHEMA_VERSION` to one above the version recorded when it lands and appends `preparations.sql` to the schema list that 065 introduces. An older catalog is refused like any other version; the autonomous objective permits resetting development catalogs. If another spec lands in between, PREP still takes the next number.
- **R3 Profiles and evidence.** A bundled, versioned manifest `assets/profiles/profiles.json` is embedded the way `seed.json` is. It names PixInsight/WBPP, Siril and SETI Astro Suite Pro. Capability classes are `input` (file list, folder or configuration), `layout`, `configuration` (value overrides), `productInput`, `inputWrite`, `recognizedOutput` and `launch`. Each class is verified, unsupported or unknown. Verified and unsupported require evidence: installed probe or documentation, reference, covered application versions and recording date. The loader refuses a verified or unsupported class without evidence. A profile reads verified only when every class is verified or unsupported (PREP-FR-01). The shipped manifest starts with every class unknown; only the qualification task changes it, with citations (D04, "Verification still required"). Tests inject manifests. Alternative: the legacy seeds carry no evidence.
- **R4 Installation scope.** Locating an executable records its path, file identity, size, modification time and observed version. The version comes from the macOS bundle `CFBundleShortVersionString` through `plist`; elsewhere it is unknown. Evidence applies only when it lists the observed version, so an unknown or unlisted version leaves version-bound classes unknown for that installation. Locating never runs the executable (J23 S8). Basis: D04 installed or documented evidence.
- **R5 Generic Open in.** A generic application has an executable and an argument list. Arguments go to the process as separate argv entries with no shell, and the placeholders `{viewFolder}`, `{inputList}` and `{outputFolder}` are substituted whole. Every class is unknown and the profile never reads verified, so Linked and Direct source are refused and Copy or supported Clone is offered (PREP-FR-02, D04, J23 S9).
- **R6 Executable at launch.** Launch uses the located path. Presence and identity are checked immediately before spawning; a missing executable yields ExecutableMissing with Choose application and Reveal View. No other installation is substituted: macOS launches `open -a` with the located bundle path, not bundle-id dispatch, which could open another copy. A changed identity re-reads the version and re-applies R4; when the evidence a prepared mode relies on no longer applies, Open is blocked and names the class.
- **R7 Launch arguments.** A profile passes the View to the application only through its verified `launch` evidence. With `launch` unknown, the application starts with no arguments, and review and Open state that the View path is not passed; Reveal View stays available. Basis: PREP-FR-01 forbids invented APIs.
- **R8 Mode suggestion and mixing.** Linked View with symlinks is suggested when `inputWrite` is verified read-only and the profile's input and layout evidence fit. Otherwise Copy, or Clone where supported, is suggested, and Linked and Direct source read refused with the input-write risk named (PREP-AC-11). A mode never changes automatically. One preparation may mix modes per item (D04): every item whose mode differs from the View mode is listed with path and footprint and needs explicit approval. D04 settles J24 G3.
- **R9 Links.** A symlink stores the absolute native source path and may cross volumes. Review names its limits: it dangles if the source moves or goes offline, and the application may resolve the target. A hardlink needs an explicit choice and an eligibility check: the source location's volume equals the destination parent's volume, the destination is writable and the source readable, Linux `protected_hardlinks` ownership holds, and the filesystem type is on the hardlink list. Link support is read without writing to the destination, from the filesystem type (`statfs` on macOS and Linux, the volume filesystem name on Windows). Types not on the qualified lists, including network and FAT-family filesystems, read link support unknown, so Linked is not offered there (PREP-AC-03, J24 S13). A failed eligibility check or creation blocks the item and never copies (PREP-AC-08).
- **R10 Clone.** Clone is offered only where a qualified primitive exists: macOS `clonefile` with the source and destination parent on the same APFS volume. Linux FICLONE and Windows block cloning read unsupported until qualified on that platform. A clone is re-read and hashed like a copy. Its footprint reads zero additional bytes at creation, labelled as growing when either side changes.
- **R11 Direct source.** Direct source needs `inputWrite` verified read-only and verified file-list or configuration input. PREP writes the list or configuration into the View's control folder and creates no image link or copy. A folder handoff needs a verified folder-consumption rule; applied to each source folder, it must yield exactly that folder's reviewed members. Otherwise the folder handoff is refused and alternatives are listed (PREP-AC-04). The rule is checked at review and again immediately before launch.
- **R12 Corrected metadata.** The catalog value of a field is the asset's effective metadata, and for focal length and pixel size the Confirmed equipment association of its session (J23 S10). For each asset and field whose catalog value differs from the observed header value, review shows both and the value the application will read. The options are supported configuration (only with verified `configuration` evidence), isolated patched Copy or Clone (only with a qualified keyword mapping), accepting the source value, or excluding the input. Exclusion is VSEL's Exclude from View, which makes a new membership revision and needs a new review; PREP never edits membership. Linked and Direct-source entries always deliver the header value. Choosing patched copies in a Direct-source View changes those items' mode and needs approval. A correction never reads delivered while the application reads the original (PREP-FR-03, D15).
- **R13 Patched copies.** PREP stages a verified plain copy or clone, then calls the shared `Header::update_file` on the staged file, never on an original. Verification re-reads the staged file: the mapped keywords hold the catalog values, and every other keyword and the data unit equal the source's. The entry records its own SHA-256 beside the source basis. The field-to-keyword mapping is qualified by fixture tests; it writes the keyword the observed value came from, or the qualified default keyword when the header lacks one. A field without a qualified keyword reads patch unsupported and keeps the other options.
- **R14 View location.** The suggested parent is the one in the most recently saved handoff settings of any View; on first use there is no parent. The suggested folder name is the View name through the `safe-filename` rules, suffixed `-2`, `-3` and so on while that name exists in the parent at review time. Settings record the parent path and folder identity. Review blocks an existing folder of that name, an unavailable parent, and a parent whose identity differs from the recorded one, so no other drive is used. Prepare re-validates the parent and creates the View folder with create-new semantics. An existing directory is never reused, cleared or written into (PREP-FR-06, D09).
- **R15 Output location.** The default is `<View>/output/`. An override parent gets `<override>/<View folder name>/`, never the override itself. The location and its folder identity are recorded on the preparation for RES discovery and STO cleanup, and created with create-new semantics at Prepare (PREP-FR-07).
- **R16 Review.** A review is a durable catalog record and writes no file. It reads the View revision, settings, application evidence, calibration handoff, source presence through no-follow fingerprints, the destination probe and free space. It lists each item's mode, link type, destination, footprint and blocks, each alternative with its footprint, the operation count, the excluded count, total footprint and free space, and the saved criteria apart from browsing filters. It hashes nothing. Confirmation confirms membership and criteria and approves exactly the listed per-item changes; a stale View, settings or application revision is Conflict (PREP-FR-08, D02).
- **R17 Blocked items.** Unresolved, offline, unreadable or retired members, members that are not library assets, unresolved calibration needs, ineligible link items and destination collisions are blocked items named with their paths. Confirmation and Prepare remain possible, but a preparation with any blocked item ends Partial at best and offers no verified Open. Unknown or omitted inputs never count as prepared, and no quality decision changes (PREP-FR-08, PREP-AC-13).
- **R18 Prepare and D19.** Start commits the preparation, its planned item journal and a Running operation in one transaction before any filesystem action (constitution Tier 1) and rechecks free space against the remaining footprint. Each chunk of up to 16 items commits its in-progress intents, with staging names, before the effects and its outcomes after. Per item, PREP opens the source through the contained reader, requires the reviewed fingerprint, hashes it and compares every recorded digest; a mismatch blocks the item and names the drift. A symlink is created after the hash. A hardlink uses `linkat` without following, and the new entry's identity must equal the source's. Copies, clones and patched copies are staged in the control folder, synced, re-read, hashed and renamed into place without replacing. The SHA-256 at the effect becomes the item's recorded basis. Sources are only read.
- **R19 Terminal states.** Prepared: every item is prepared and verified, and a no-follow listing of the consumed layout holds exactly the prepared entries. Partial: some items are prepared and some are blocked, or the layout holds unexpected entries. Failed: no item is prepared or the View folder could not be created. Canceled and Paused follow requests. The start acknowledgment reads Running, never success (PREP-FR-09).
- **R20 Cancel and Pause.** Both are offered throughout Running and take effect at item boundaries; an in-flight staged copy may be abandoned and stays a recorded leftover. Canceled ends that attempt; Paused waits for Retry. Basis: "where safe" in PREP-FR-09; an item boundary is always safe because nothing is removed. This settles J24 G4.
- **R21 No removal.** PREP never removes, trashes or rewrites a file, including its own unverified staging leftovers. Leftovers are recorded entries with role leftover, kept in the control folder outside the consumed layout, for STO's reviewed cleanup (STO-FR-10, constitution II).
- **R22 Restart.** On open, Running preparation operations become Paused and their in-progress items uncertain. Verifying launches become Interrupted, and launching records become OutcomeUnknown. Boot performs no filesystem effect, and the paused operation is the explicit resume prompt the constitution requires. Retry reconciles each uncertain item against its recorded intent: kind, link target, identity and digest. A match is prepared, absence is redone, and anything else blocks the item. Nothing is inferred from file names (D09).
- **R23 Retry.** Retry is a new attempt over the planned, blocked and uncertain items of the same revision in its own folder, after revalidating the review basis. It never changes membership; a newer View membership revision needs a new review and revision. Retry is allowed from Partial, Failed, Canceled and Paused.
- **R24 Revisions.** A review of a newer membership revision proposes a new preparation revision in a new folder. Older revisions keep their state and entries for comparison, and Open applies to the requested Prepared revision with non-current revisions labelled. When a newer revision of the same View reaches Prepared, every older revision records it as `supersededBy`, which scopes STO's cleanup of replaced entries; removing them is STO's. On a Complete View, PREP refuses a new revision and Retry until Reopen; Open and Reveal stay available because they create nothing (PREP-FR-11, PREP-AC-12, D09).
- **R25 Open.** Open applies to a Prepared revision. Before spawning, the launch record re-verifies every basis (D19):
  - A link must still be a link to its recorded target, and its source must match identity and SHA-256.
  - A hardlink must match identity and SHA-256.
  - A copy, clone or patched copy must match its entry SHA-256.
  - A Direct-source input must match its source SHA-256, and a handoff file its own SHA-256.

  Any mismatch blocks the launch and names the drift. The executable check follows (R6). Outcomes are Launched, Blocked, ExecutableMissing or LaunchFailed. PREP monitors no process, and no outcome changes the View, its decisions or completion (PREP-FR-10).
- **R26 Reveal View.** Core verifies the recorded View folder identity and the shell calls `tauri_plugin_opener::reveal_item_in_dir`. No webview opener capability is granted.
- **R27 Retire interplay.** `PreparationReferences` implements `AssetReferences` with kind View. It names each preparation revision whose items hold the asked assets, with the preparation's record revision, so a change after review refuses retire confirmation. Retired copies keep their entries, read unresolved in later reviews and block Open (D11).
- **R28 Naming.** Commands use the `prep_` prefix in `commands/application_handoff.rs`, apart from the legacy `preparedview_*` commands.
- **R29 Copy choice.** A member is one logical capture with one or more registered copies (D16). Review hands off one copy per member: the first copy in VSEL's copy order that is Available and matches its fingerprint. A hardlink item prefers a copy on the destination volume. Review names the chosen copy. Prepare and Open never substitute another copy, so a chosen copy that becomes unreadable blocks its item (PREP-AC-05). Basis: D19 binds effects to the reviewed basis.

## Qualification

Real capability evidence for Siril, PixInsight/WBPP and SETI Astro Suite Pro is an implementation prerequisite (D04). Each class stays unknown until a cited installed probe or documentation records it; a profile with an unknown `inputWrite` never receives Linked or Direct-source handoff. Generated FITS and XISF fixtures must cover five sessions with 208 lights, one source folder that also holds six excluded frames, a catalog FILTER correction and a confirmed-equipment focal length absent from the header. They must also cover a FAT-family disk image without link support, a second APFS volume for hardlink refusal, a colliding folder, a detached parent, three unreadable inputs and SQLITE_FULL. Every scenario compares source hashes before and after. Linux and Windows link, clone and permission behavior remain explicit platform gates. Real development-MCP evidence remains an acceptance gate, and no legacy test result proves the rebuild.
