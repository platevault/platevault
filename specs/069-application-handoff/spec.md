## User Scenarios & Testing

### User Story 1 - Application preparation: profiles, input modes, locations, prepare and open (Priority: P1)

This feature owns the Prepare step of a processing run (View), which always belongs to a Project. It turns a run's reviewed membership into a verified handoff for a maintained profile or a generic Open in..., with the run's Results folder beside its prepared folder. The run view is Symlinks (the default) or Copies, and Copies are made as file clones where the volume supports them. A mosaic run group prepares every panel run under one group folder, and each panel run has its own Results folder. Finishing the run offers to remove its view, ticked for Copies and unticked for Symlinks, and a view the user kept is cleaned up in the Project's Wrap up. The app never runs processing.

**Why this priority**: This feature owns the workflow steps listed below without imposing unrelated product features.

**Independent Test**: Exercise the acceptance scenarios through the running product with isolated inputs. Existing baseline code does not prove the redesigned behavior.

## Requirements

### Functional Requirements

- **PREP-FR-01**: The required profile targets are PixInsight/WBPP, Siril, and SETI Astro Suite Pro. Decision D04 requires verified input, layout, configuration, product-input capabilities and recognized output evidence before any verified-profile claim. PlateVault detects installed applications: on Windows from the registry, on macOS from the installed application bundles, and on Linux from standard paths. The user can also add an application by picking its executable through the native file dialog. Every application, detected or added, has launch arguments the user can edit. Prepare's profile choice is a dropdown of the detected and added applications only. Unsupported configuration is named. No profile invents an API or claims that renaming files overrides headers. (D-W83)
- **PREP-FR-02**: Generic Open in... takes a configured executable and launch arguments, without claiming a verified profile. Adding one is the same Add application… step as PREP-FR-01. Settings > Applications shows no input-write field; input-write behavior stays a profile capability that is named only where it refuses a mode (PREP-FR-04, PREP-AC-11) (D-W83).
- **PREP-FR-03**: Corrected metadata: the review shows the catalog value next to the value the application will read. Options: supported application configuration, isolated patched copies, accepting the source value, or excluding the input. Originals and links are never patched. A correction is never claimed as delivered while the tool still reads the original value. (D-W3)
- **PREP-FR-04**: Run view modes: **Symlinks**, the default, and **Copies**. The mode is chosen per run in Prepare, and Settings holds the default. In Symlinks mode the run folder holds symlinks to the catalogue originals, with the footprint "Linked · 0 B". In Copies mode the run folder holds temporary copies, with the footprint "N frames copied · X GB". Where the source and the run folder are on one volume whose filesystem supports file clones (APFS, Btrfs, XFS), each copy is a copy-on-write clone, and the footprint reads "N frames copied · X GB (cloned)". There is no Automatic mode, no file-list or Direct-source mode, no separate Clone mode, no hard links and no junctions, and PlateVault never falls back from one mode to another on its own. Review shows each mode's semantics, limits and storage. Unknown or write-prone input behavior refuses Symlinks and offers Copies under root decision D04. Runs take FITS, XISF, DNG and camera RAW (CR2, CR3, NEF, ARW and the like) only; SER video is out of scope. (D-W81)
- **PREP-FR-05**: Withdrawn (D-W81). There is no Direct-source mode: every run hands the application a run folder of Symlinks or Copies.
- **PREP-FR-06**: Run location: a single run prepares to `<output>/<Project>/<Run>/`, where `<output>` is the last chosen parent folder; on first use there is no assumed root. Each later prepared revision goes to `<Run> (rev 2)/` and so on beside it. A run group uses the layout in PREP-FR-12. An existing directory is never reused or cleared; when the proposed folder already exists, preparation asks for another name or location. An unavailable parent prompts a new choice and is never silently replaced by another drive. (D-W3, D-W38, D-W51, D-W67)
- **PREP-FR-07**: Results go to the sibling folder `<output>/<Project>/<Run> Results/`, outside every prepared folder, so the application never reads its own output as input. In a run group, each panel run's Results go to its own folder `<output>/<Project>/<Mosaic> Results/Panel N/`, so a Result's panel is known from where it was written. The group Result, the assembled mosaic, goes to `<output>/<Project>/<Mosaic> Results/Assembled/`. Every Results folder of a run group sits outside the prepared group folder `<Mosaic>/` and every later group folder, so an application that loads the group folder never reads its own output as input either. One Results folder serves every prepared revision of the run or panel run; a later group revision `<Mosaic> (rev 2)/` gets no Results folder of its own. An override parent replaces `<output>` for the Results folders only and keeps the Project level: `<override>/<Project>/<Run> Results/`, `<override>/<Project>/<Mosaic> Results/Panel N/` and `<override>/<Project>/<Mosaic> Results/Assembled/`. An override parent inside a prepared folder of the run or group is refused, so every Results folder stays outside every prepared folder. The location is recorded for Result discovery. (D-W3, D-W38, D-W51, D-W67, D-W73)
- **PREP-FR-08**: Review preparation shows the run's Project and subject, the immutable selection, profile, source references, calibration choices, exceptions, excluded count, paths, mode, operation count, footprint, and free space. Saved criteria are shown apart from browsing filters and confirmed. Source presence, collisions, and permissions are checked. Any subset that cannot use the mode is listed with paths and footprint, and per-item mode changes need approval. Unknown or omitted inputs never count as prepared. (D-W1, D-W9)
- **PREP-FR-09**: Prepare run shows Running and progress, cancel or pause where safe, and per-item failures. It ends in exactly one of Prepared, Partial, Failed, Canceled, or Paused. Success requires the prepared entries to match the recorded selection and each source's SHA-256 snapshot taken during Prepare. Copies, cloned or not, are durably written and re-read against that snapshot; an isolated patched entry may differ only by its reviewed header change. Symlink entries must resolve to the snapshotted source identity. Immediately before terminal success, each source's current identity and digest must still match its snapshot. Drift, a destination mismatch or an unreadable source blocks the item. So does an observation fingerprint differing from the confirmed membership. So does a snapshot differing from any D19 basis recorded for the input, such as its quality decision, logical-capture proof, acceptance, adoption or calibration assignment digest. Automatic calibration assignments are re-verified exactly like accepted ones (CAL-FR-08). A blocked item never counts as prepared. Partial lists succeeded and blocked items. Sources are untouched. (D-W3, D-W5)
- **PREP-FR-10**: After verified success, the user gets Open in the chosen app, Reveal run folder, and preparation details. Immediately before each launch, Open re-verifies under D19 the bytes the application will read: copies and symlink targets, each against its preparation snapshot. Drift refuses the launch and names the changed items, and the run reads unverified until those bytes return or a reviewed repreparation replaces them. PlateVault does not re-verify the originals after the run. Launching is not processing completion, and closing the application never finishes the run. A missing executable offers Choose application or Reveal run folder. A launch failure keeps the run and its decisions. (D-W3, D-W81)
- **PREP-FR-11**: A revised selection needs a new review. Each new preparation revision is materialized in a new reviewed run folder, `<Run> (rev 2)/` and so on beside the earlier ones, and never replaces, reuses or clears an existing preparation in place (D09). A previous preparation can be kept for comparison. Removing replaced entries follows STO cleanup rules. (D-W3, D-W51, D-W67)
- **PREP-FR-12**: Prepare all on a run group opens one review covering every panel run and prepares each one under `<output>/<Project>/<Mosaic>/Panel N/`, so an application such as WBPP can load the group folder. The group folder holds only the `Panel N/` folders; every Results folder of the group sits outside it (PREP-FR-07). The group's shared profile, input mode and calibration policy apply to every panel run, and per-item mode exceptions still follow D04. Calibration choices are shown and matched per panel run, and the review names each panel run whose calibration needs review (CAL-FR-11). Each panel run ends in its own outcome under PREP-FR-09, and the group lists each panel's outcome. The group reads Prepared when every panel run is Prepared, Failed when every panel run Failed, Canceled or Paused when the user cancels or pauses Prepare all, and Partial otherwise. One panel's blocked items never block another panel's items. (D-W38, D-W41, D-W51, D-W55, D-W73)
- **PREP-FR-13**: Open on a run group's folder appears only when every panel run is verified, and it re-verifies every panel's entries under PREP-FR-10 before launch. Open on a single verified panel run stays available. Each group preparation revision gets a new group folder, `<Mosaic> (rev 2)/` and so on, with a `Panel N/` folder inside it for every panel run. When the user reprepares a panel run whose Panel N folder already exists, review proposes that new group folder. The previous group folder stays until the user approves its STO cleanup. The panel runs' Results folders under `<Mosaic> Results/` serve every group revision and belong to no group folder. The user assembles the mosaic in the application and saves it to `<Mosaic> Results/Assembled/`, where it comes back as the group Result (RES). A run group never has a whole-mosaic run. (D-W38, D-W51, D-W67, D-W73)
- **PREP-FR-14**: Finish run…'s confirmation offers removing the run's view as a checkbox, with the entries it removes and their size. The box is unticked for a Symlinks view, which holds no data, and ticked for a Copies view. Confirming with the box ticked removes the view: the links the run created are deleted after the no-follow check of STO-FR-04, and copies go to the OS Trash. The view of a run that is not Finished stays. A view the user keeps is listed later in Wrap up's Clean up runs step (PRJ-FR-14), and no other place offers run clean-up. The view holds only the entries the run's preparation revisions created: prepared links and copies. Original sources, library frames and Results are never listed. Clean up never moves rejected frames to Trash; that belongs to the Project's Wrap up. Moving a run to the Project's Trash leaves its prepared folders and Results folder in place, so Restore finds them unchanged. Only Empty Trash (RES-FR-10) moves the run's prepared folders to the OS Trash, and its Results folder only when the user ticks it. Removal follows STO custody rules, including retained-original proof, OS Trash handling for copies and the checked deletion of links (STO-FR-01, STO-FR-04, STO-FR-17). (D-W26, D-W43, D-W72, D-W80, D-W81)
- **PREP-FR-15**: On Windows, symlinks need Developer Mode. PlateVault checks it during setup, in Settings and at Prepare. When it is off, Prepare in Symlinks mode is refused with "Can't prepare · symlinks need Windows Developer Mode ▸", which offers Open Windows settings, Check again and Use copies for this run. (D-W81)

### Key Entities

Use the [root vocabulary](../063-clean-rebuild-contract/spec.md#key-entities). Feature-specific evidence and decisions retain their input identity, scope, and revision.

- **Run folder**: the reviewed folder a preparation revision of one run is materialized in, `<output>/<Project>/<Run>/` for the first revision and `<Run> (rev N)/` for later ones. (D-W3, D-W51, D-W67)
- **Group folder**: `<output>/<Project>/<Mosaic>/`, or `<Mosaic> (rev N)/` for a later group revision, holding one `Panel N/` folder per panel run of a run group for one group preparation revision. It holds no Results folder (PREP-FR-07). (D-W38, D-W51, D-W67, D-W73)
- **Results folder**: the sibling `<Run> Results/` folder that receives a run's outputs from every prepared revision, outside every prepared folder. In a run group, each panel run has its own `<Mosaic> Results/Panel N/` folder, and the group Result goes to `<Mosaic> Results/Assembled/`, both outside every group folder. Under an override parent each keeps the `<Project>/` level (PREP-FR-07). (D-W51, D-W67, D-W73)
- **Prepared entry**: a link or a copy (cloned or not) created by a preparation revision. Prepared entries are the only files Clean up of a run lists. (D-W26)

## Decisions before feature approval

- Root decisions D02, D04, D09, D13 and D15 govern exact inclusion confirmation, profile qualification, input-write refusal, reviewed calibration/preparation revisions and isolated header corrections. No unsupported tool capability is claimed without evidence.
- Root decision D19 binds Prepare and Open to re-verified source and entry content.
- Workflow decisions D-W1, D-W3, D-W5, D-W9, D-W26, D-W38, D-W41, D-W43, D-W51, D-W55 and D-W67 (settled 2026-10-06) and D-W72 and D-W73 (answered 2026-10-07) place preparation inside a Project's run and add run group preparation under one group folder. They set the `<output>/<Project>/<Run>/` layout with a new folder per prepared revision and one shared sibling Results folder, and one Results folder per panel run. They limit Clean up of a Finished run to its prepared entries, and only Empty Trash sends the prepared folders of a run in the Project's Trash to the OS Trash.
- Workflow decision D-W81 (Round 7 P-PREP3, Round 8 P-TRASH2, 2026-10-12) sets the two run view modes, Symlinks by default and Copies, with no hard links or junctions, the Windows Developer Mode prerequisite, the view-removal offer at Finish run, and no re-verification of originals after a run. The owner's answers of 2026-10-14 make view removal a Finish run checkbox, unticked for Symlinks and ticked for Copies, delete a run's links after a no-follow check instead of trashing them, remove Direct source, and make Copies clone where the volume supports it.
- Workflow decision D-W83 (Round 9 user items, 2026-10-12) sets application detection, adding an application by its executable, launch arguments on every application and Prepare's dropdown of detected tools. The earlier application's detection, which this follows, is `crates/workflow/profiles/src/discover.rs`: the Windows registry (App Paths and Uninstall entries), `/Applications` bundles on macOS, and `PATH` plus known directories on Linux.
