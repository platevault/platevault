## User Scenarios & Testing

### User Story 1 - Application handoff: profiles, input modes, the View layout, Apply and Open (Priority: P1)

This feature owns a Project's View: its folder layout, its input modes, building it from the originals when the user chooses Apply, and the verified handoff to a maintained profile or a generic Open in…. Each Project has `<Processing location>/<Project>/` with `View/`, `Processing/<Tool>/` and `Output/`. The View is Symlinks (the default) or Copies, and Copies are made as file clones where the volume supports them. Apply builds a complete `View (building)/` from the originals and swaps it in, keeping the old one as `View (previous)/`. At Close, Clean up offers removing the View, ticked for Copies and unticked for Symlinks. The app never runs processing.

**Why this priority**: This feature owns the workflow steps listed below without imposing unrelated product features.

**Independent Test**: Exercise the acceptance scenarios through the running product with isolated inputs. Existing baseline code does not prove the redesigned behavior.

**Acceptance Scenarios**:

When the user opens the Apply sheet for the first time, then it shows Work/Processing/NGC 7000 HOO/ with `View/`, `Processing/Siril/` and `Output/`, 208 light entries, the mode and its limits, the footprint "Linked · 0 B", and free space. Nothing is applied until the user chooses; no silent copy occurs. For a Siril Project Copies isn't offered either, and Apply asks for another processing location (provisional, PREP-FR-17). (D-W81)

## Requirements

### Functional Requirements

- **PREP-FR-01**: The required profile targets are PixInsight/WBPP, Siril, and SETI Astro Suite Pro. Decision D04 requires verified input, layout, configuration and recognized output evidence before any verified-profile claim. PlateVault detects installed applications: on Windows from the registry, on macOS from the installed application bundles, and on Linux from standard paths. The user can also add an application by picking its executable through the native file dialog. Every application, detected or added, has launch arguments the user can edit. The View step's application choice is a dropdown of the detected and added applications only. Unsupported configuration is named. No profile invents an API or claims that renaming files overrides headers. (D-W83, D-W100)
- **PREP-FR-02**: Generic Open in... takes a configured executable and launch arguments, without claiming a verified profile. Adding one is the same Add application… step as PREP-FR-01. Settings > Applications shows no input-write field; input-write behavior stays a profile capability that is named only where it refuses a mode (PREP-FR-04, PREP-AC-11) (D-W83).
- **PREP-FR-03**: Corrected metadata: the user corrects a session's metadata in its intake flow (LIB-FR-20), and Apply creates and changes no correction. Apply delivers every correction recorded on the Project's sessions: through the application's supported configuration where its profile reads corrected values that way, and otherwise as isolated patched copies. The Apply sheet shows the count, "N corrected values", and lists each value with its session, field, header value and corrected value, naming the route. It offers no per-value choice: no accepting the source value and no excluding an input. Originals and links are never patched. A correction is never claimed as delivered while the tool still reads the original value. Provisional, from the prototype: in Symlinks mode an input that needs a patched copy is placed as an isolated patched copy beside the links. (D-W122, Round 9 C15)
- **PREP-FR-04**: View modes: **Symlinks**, the default, and **Copies**. The mode is a Project setting, with the default in Settings, and switching it is a pending change that Apply carries out (VSEL-FR-12). In Symlinks mode the View holds symlinks to the catalogue originals, with the footprint "Linked · 0 B". In Copies mode the View holds temporary copies, with the footprint "N frames copied · X GB". Where the source and the View are on one volume whose filesystem supports file clones (APFS, Btrfs, XFS), each copy is a copy-on-write clone, and the footprint reads "N frames copied · X GB (cloned)". There is no Automatic mode, no file-list or Direct-source mode, no separate Clone mode and no junctions, and PlateVault never falls back from one mode to another on its own. PlateVault never makes a hard link, to an original or between its own copies. Each copy is an independent file, so a tool that writes one View entry changes no other. The Apply sheet shows each mode's semantics, limits and storage. Unknown or write-prone input behavior refuses Symlinks and offers Copies under root decision D04. A View takes FITS, XISF, DNG and camera RAW (CR2, CR3, NEF, ARW and the like) only; SER video is out of scope. (D-W81, D-W98)
- **PREP-FR-05**: Withdrawn (D-W81). There is no Direct-source mode: every View holds Symlinks or Copies.
- **PREP-FR-06**: Each Project has `<Processing location>/<Project>/`, where the processing location is the last chosen parent folder; on first use there is no assumed root. It holds `View/`, the inputs PlateVault places; `Processing/<Tool>/`, each tool's working and output folder, one per tool; and `Output/`, the Project's Results (RES-FR-01). Apply builds a complete `View (building)/` from the originals only and never moves or reuses entries from the current View. After checking the new folder it swaps it in, and the old one becomes `View (previous)/` (STO-FR-10). The copy cost is accepted. Apply needs every original the build uses online: if any is offline, nothing changes and the sheet lists the offline originals (VSEL-FR-14). A pinned calibration file that has changed or is missing refuses Apply the same way, with a link to reassign it (CAL-FR-08, D-W113), and Apply waits while `View (previous)/` holds files the user hasn't reviewed (VSEL-FR-14, D-W110). An unrelated folder already at the Project's path is never adopted, reused or cleared; Apply asks for another name or location. An unavailable parent prompts a new choice and is never silently replaced by another drive. (D-W98, D-W100)
- **PREP-FR-07**: Tools work only in `Processing/<Tool>/`, outside `View/`, so an application never reads its own output as input, and they never write into `Output/` (RES-FR-01). PlateVault never hands a tool the whole Project folder. A tool rerun may overwrite earlier files in `Processing/`; duplicating the Project is the way to keep them. (D-W93, D-W98)
- **PREP-FR-08**: The Apply sheet (VSEL-FR-14) also shows the Project, the application, the input mode, source references, the calibration of each group and night, the excluded count, paths, the operation count, footprint and free space. Source presence, collisions and permissions are checked. Any subset that cannot use the mode is listed with paths and footprint, and per-item mode changes need approval. Unknown or omitted inputs never count as placed. (D-W100)
- **PREP-FR-09**: Apply shows Running and progress, cancel where safe, and per-item failures, and it ends Applied, Failed or Canceled. Success requires every entry of `View (building)/` to match the Project's inputs and each source's SHA-256 snapshot taken during the build. Copies, cloned or not, are durably written and re-read against that snapshot; an isolated patched entry may differ only by its reviewed header change. Symlink entries must resolve to the snapshotted source identity. Immediately before the swap, each source's current identity and digest must still match its snapshot. Drift, a destination mismatch or an unreadable source blocks the item, and so does a snapshot differing from any D19 basis recorded for the input, such as its quality decision, logical-capture proof, adoption or calibration assignment digest. Pinned calibration is re-verified like any other input (CAL-FR-08). A blocked item fails the build: the current View is never replaced by an incomplete one, `View (building)/` is kept for Retry or removed by Cancel, and the sources are untouched. (D-W5, D-W100)
- **PREP-FR-10**: After Apply, the user gets Open in the chosen app, Reveal View, and Apply details. Immediately before each launch, Open re-verifies under D19 the bytes the application will read: copies and symlink targets, each against its Apply snapshot. Provisional: a symlink that Archive repointed is checked against the archive copy that the repoint recorded (STO-FR-06), so the repoint isn't read as drift. Drift refuses the launch and names the changed items, and the View reads unverified until those bytes return or a new Apply replaces them. PlateVault does not re-verify the originals after a tool runs. Launching is not processing completion, and closing the application never closes the Project. A missing executable offers Choose application or Reveal View. A launch failure keeps the Project and its decisions. (D-W81, D-W100)
- **PREP-FR-11**: Withdrawn (D-W100). There are no preparation revisions: each Apply builds a complete new View from the originals and swaps it in (PREP-FR-06).
- **PREP-FR-12**: Withdrawn (D-W94). There are no run groups; a mosaic's panel groups sit in the View under PREP-FR-16.
- **PREP-FR-13**: Withdrawn (D-W94). There is no group folder or group Open; Open hands the tool the Project's View.
- **PREP-FR-14**: Withdrawn (D-W97). Removing the View at Close is the Clean up step of the Project's Wrap up (STO-FR-01).
- **PREP-FR-15**: On Windows, symlinks need Developer Mode. PlateVault checks it during setup, in Settings and at Apply. When it is off, Apply in Symlinks mode is refused with "Can't apply · symlinks need Windows Developer Mode ▸", which offers Open Windows settings, Check again and Use copies for this Project (provisional copy). Provisional: a Siril Project is refused in Copies mode too and isn't offered Use copies for this Project, because its `Processing/Siril/` sets are symlinks (PREP-FR-17). (D-W81)
- **PREP-FR-16**: The View layout is `View/`, then a `GROUP_<name>/` or `PANEL_<name>/` folder per group only when the Project has several groups (PRJ-FR-28), then a `NIGHT_<date>/` folder per night with a hyphenated date, such as `NIGHT_2026-10-14`, because in WBPP an underscore ends a keyword value. Lights and flats always sit in `NIGHT_` folders, in folders inside `Lights/` and `Flats/` named by the FILTER value with no `FILTER_` prefix, which also gives Siril its per-filter sets. Their names also carry any `GAIN_` and `OFFSET_` parts and, for lights, the provisional exposure part, as set out below (D-W108). Flats sit in the night folder of the lights they calibrate, placed by the pinned assignment, not by the date they were taken. Darks and bias sit in `Darks/` and `Bias/`, at the top with one camera and inside each group when the Project has several cameras, shared and untagged when every light set there uses the same version. When a Project mixes versions with the same settings, every dark or bias with those settings goes into the night folders of the lights that use it, because in WBPP an untagged dark may match every night. A one-group Project has no group folder, even when its group is a mosaic panel. When a Project mixes gain or offset, those values are part of the folder name itself, as in the owner's example `HA_GAIN_120_OFFSET_50_300s` (filter, gain, offset, exposure). The `GAIN_<value>` part appears when it mixes gain and the `OFFSET_<value>` part when it mixes offset, as WBPP Pre keywords. A Project with one gain and one offset gets neither part. No entry is a hard link (PREP-FR-04). Provisional: a flat set or master used on several nights gets its own copy in each night folder that uses it, made from its original and cloned where the volume supports clones; with Symlinks each folder gets a link. Provisional: a second flat set for the same night, filter and group, such as after a rig version change mid-night, gets its own folder, `NIGHT_2026-10-14-2`. Provisional: the parts follow the order of the owner's example. A light folder always ends in its exposure, such as `Lights/Ha_300s/` or `Lights/Ha_GAIN_120_OFFSET_50_300s/`. A flat folder has no exposure part, because a flat's exposure varies per filter and night and WBPP matches flats by filter. It takes the gain and offset of the lights it calibrates, such as `Flats/Ha_GAIN_120/`. Darks and bias get a folder inside `Darks/` and `Bias/` only when the Project mixes gain or offset, named from the parts it mixes, and for darks then the exposure, such as `Darks/GAIN_120_300s/` and `Bias/GAIN_120/`. Spaces become hyphens in group folder names, such as `PANEL_Panel-1/` (PRJ-FR-27, D-W114). Open: whether the rule also covers the Project folder, shown as `NGC 7000 HOO/` in PREP-AC-01, is not decided (D-W114). (D-W81, D-W95, D-W99, D-W108, D-W114)
- **PREP-FR-17**: Tool layouts. Siril: `Processing/Siril/<set>/` holds Siril's standard `lights/`, `flats/`, `darks/` and `biases/` as symlinks into View, one set per group and filter, and per night when nights have their own flats, merged with Sirilic; provisional: a test must show that Siril follows folder links. Siril's sets are symlinks in either View mode, so a Siril Project needs symlinks even in Copies mode. Provisional, as a consequence: where PlateVault can't create symlinks, Apply for a Siril Project is refused in both modes, and no junction, copied Siril layout or other fallback is tried (D-W81). On Windows with Developer Mode off it reads "Can't apply · symlinks need Windows Developer Mode ▸" and offers Open Windows settings and Check again. It doesn't offer Use copies for this Project, because Copies of the View don't give Siril its sets. On a processing location that can't hold symlinks it asks for another location (PREP-FR-06). Provisional notes the Apply sheet shows for the other tools: WBPP adds `View/`, with the NIGHT keyword for Pre only, GROUP (or PANEL) for Pre and Post, the registration reference "auto by GROUP" and the output directory `Processing/WBPP/`. When folder names carry `GAIN_` or `OFFSET_` parts, the WBPP note also lists GAIN or OFFSET as Pre keywords (D-W108). APP loads each `NIGHT_` folder as a session, with the working folder `Processing/APP/`. DSS uses one file group per `NIGHT_` folder, darks and bias in the Main group and the output `Processing/DSS/`, and writes `.Info.txt` next to each light (VSEL-FR-20). SASpro loads from `View/`, with a session tag per night taken from file names and the stacking folder `Processing/SASpro/`. SASpro matches darks by exposure, gain, offset, temperature and size, not by session or date, so a Project that mixes dark versions with the same settings needs two passes in SASpro, and the Apply sheet says so. (D-W81, D-W99, D-W108)
- **PREP-FR-18**: If a file in View is in use on Windows, Apply waits after the build, reading "Waiting for a tool to release a file in View", and continues by itself once the file is released. Cancel keeps the old View. Provisional: PlateVault names the holding app through Windows Restart Manager, which is untested. (D-W100)
- **PREP-FR-19**: An entry keeps its name for life. When a file with the same name joins, the new entry takes a distinguishing suffix and the existing entry keeps its name (D-W114). Provisional: one PlateVault operation runs per Project at a time, so Apply, Wrap up and Archive refuse while another runs on that Project and name it. (D-W100, D-W114)

### Key Entities

Use the [root vocabulary](../063-clean-rebuild-contract/spec.md#key-entities). Feature-specific evidence and decisions retain their input identity, scope, and revision.

- **Project folder**: `<Processing location>/<Project>/`, holding `View/`, `Processing/<Tool>/` and `Output/`. (D-W98)
- **View**: the input folder Apply builds. It is `View (building)/` while Apply runs, and the replaced one is `View (previous)/` until it is empty. (D-W100)
- **View entry**: a link or an independent copy (cloned or not, never a hard link) that Apply placed. Clean up lists the View's entries and, provisionally, whatever `View (previous)/` still holds, including files PlateVault didn't place, each unticked (STO-FR-01). (D-W81, D-W97, D-W98, D-W99, D-W100)

## Success Criteria

### Measurable Outcomes

- **PV-PREP-SC-01**: Every acceptance scenario produces its stated outcome and refusal behavior.
- **PV-PREP-SC-02**: Every owned interaction step has a requirement and independently observable acceptance evidence.
- **PV-PREP-SC-03**: Original inputs remain unchanged except through separately reviewed and approved filesystem operations.
- **PV-PREP-SC-04**: In the Clean up fixtures, zero original sources or library frames are listed, and zero files go to Trash other than the View's entries and the `View (previous)/` files the user ticked. (D-W43, D-W97)
- **PV-PREP-SC-05**: In the Apply fixtures, zero entries are moved or reused from the current View, and a refused or failed Apply leaves the current View byte-identical. (D-W100)

## Decisions before feature approval
