# Observing plans research

## Decision

Store saved sites, the default site, Planned marks, reminder subscriptions and delivery records as Tier 1 rows in the clean library catalog, `crates/persistence/library`, through its single serialized writer. Compute observing windows in a pure `platevault_core::planning` module that composes skymath 0.7.2 twilight, altitude-crossing, Moon-crossing and separation primitives, with a bundled IANA time-zone database. Run reminders in an in-app scheduler that starts only for enabled subscriptions and records each delivery identity before it submits a notification. Render calendar snapshots in Rust and save them through the native save dialog. The isolated rebuilt shell exposes `planning_*` commands. The plan reuses no legacy settings store, frontend astronomy or notification bootstrap.

## Source evidence

Read at `97ca51be`, the reviewed 064 backend with the 065 plan. No runtime behavior is claimed from reading.

It provides `altitude_crossings` around the transit nearest a given instant, geometric and without refraction (`src/observer.rs:432-485`). ## Resolved ambiguities

Each entry records the decision, its basis and the alternative considered. Where the spec is silent, the default follows the root [decision register](../063-clean-rebuild-contract/decisions.md).

- **R1 Storage and schema version.** Planning tables live in `crates/persistence/library/src/planning.sql`, appended to the catalog schema after `projects.sql`, with SQL in `src/planning.rs`. The dependency order is 064 (version 6), then 065 (version 7), then 072. The integration owner sets `SCHEMA_VERSION` and the `catalog_meta` row to one above the version on its integration base. That is 8 when no sibling from 066 to 071 lands first. Any other recorded version is refused, and the autonomous objective permits resetting development catalogs. Basis: one serialized writer, foreign keys to `targets`, and one reader snapshot for the Target overview. Alternative: a separate planning crate needs a second writer connection.
- **R2 Site record.** A site has a trimmed non-empty name unique among sites, latitude in [-90, 90], east-positive longitude in [-180, 180], optional finite elevation in meters, and an IANA zone name chosen by the user. Its decision revision starts at 1. The time zone is never derived from coordinates. The plan adds no removal command, because the spec names none. Basis: PLAN-FR-01 and the legacy `ObserverSite` fields, without its JSON settings store. Alternative: coordinate-to-zone lookup adds a boundary dataset that the spec does not require.
- **R3 Time-zone database.** `platevault_core` uses `jiff` 0.2 with the bundled database, so every platform and test resolves the same rules. Saving a site validates the zone name against that database. Basis: DST-correct night boundaries, local window times and calendar text must agree between the UI and the `.ics`. Alternatives: `chrono-tz` or `time-tz` also bundle rules, but `jiff` is maintained and strict about zone names. A fixed UTC offset is wrong across DST. Frontend `Intl` conversion would move computation out of Rust (PLAN-FR-08).
- **R4 Planning site.** The planning site is a parameter of each window request, never a stored record. The default site is the one stored planning setting. Basis: PLAN-FR-01 requires the selector to stay independent of Projects and capture sites, and a request parameter cannot change either. Alternative: a stored active-site pointer, as in legacy settings, adds UI state without a requirement.
- **R5 Night.** A night is labeled by the site-local date of its evening. It runs from local noon on that date to local noon on the next date, in the site's zone, so DST nights last 23 or 25 hours. Windows are clipped to the night. Basis: one stable label per night for windows, reminders and export ranges.
- **R6 Criteria.** Altitude is the minimum geometric target altitude above a flat horizon, in [0, 90), without refraction, as skymath computes it. Darkness is the Sun below the civil, nautical or astronomical threshold. The Moon criterion is `none`, `below_horizon` with the Moon's center below the geometric horizon, or `min_separation` in (0, 180) degrees whenever the Moon is above the horizon. Minimum duration is whole minutes from 1 to 1440. Every criterion is explicit in each request. Basis: PLAN-FR-02 names these four criteria, and skymath supplies each quantity. Alternatives: refraction, horizon profiles and Moon illumination limits are not required by the spec.
- **R7 Window composition.** For each night the core intersects the dark interval from `twilight`, the target-above intervals from `altitude_crossings`, and the Moon-allowed intervals. It queries crossings at the night's start, middle and end and merges the results, so a target that sets and rises within one night yields two windows. Moon-up intervals come from `moon_crossings` at the same instants. Separation intervals come from 10-minute samples of `lunar_separation`, with each sign change bisected to one second. Boundaries are rounded inward to whole minutes, so every listed minute meets the criteria. Windows shorter than the minimum duration after rounding are dropped. A night without a window states why. Basis: skymath crossings bracket one transit only, and no shared window function exists (D18). Alternative: adding an interval function to skymath first. It may move upstream through a reviewed skymath change if qualification shows reuse value.
- **R8 Target eligibility.** Windows need a saved Target with `icrs` coordinates. A seed Target is saved through `library_save_target` first, as 065 requires for framing. Missing coordinates read `target_coordinates_unknown`, and another frame reads `unsupported_coordinate_frame`. Neither becomes a zero position. Basis: D01 and D12 never treat unknown evidence as known.
- **R9 Accuracy qualification.** A committed fixture holds astroplan reference instants with pressure 0, so no refraction applies, for twilight, target and Moon crossings. It covers Backyard and the second site, a DST-change night, a never-dark summer night at high latitude, a polar always-dark night and a target that sets and rises in one night. Unrounded boundaries must agree within 180 seconds, the skymath Moon bound. Windows are recomputed and compared to the reference, never the reverse. Basis: ADR 0003 states that existing evidence does not certify planning accuracy.
- **R10 Planned mark.** Mark Planned is a row in `target_plans`, keyed by Target, with its own decision revision. It never changes the Target row or its decision revision. Basis: 065 snapshots the Target revision for framing, so a Target revision change would mark every framing Project changed. Alternative: a `planned` column on `targets` edits LIB storage and that revision.
- **R11 Independent opt-ins.** Mark Planned enables nothing, and enabling notifications marks nothing Planned. Both appear in the Target overview. Basis: PLAN-FR-03 lists two explicit opt-ins, and D07 starts notifications disabled. Alternative: coupling reminders to the Planned mark adds a rule the spec does not state.
- **R12 Reminder subscription.** Reminders are per Target. A review reads the current default site, its revision, the explicit criteria, the lead time, the permission state and the delivery capability, and writes nothing. Activation repeats those values and commits only when the default site and its revision still match. Lead time is whole minutes from 1 to 1440. Missing criteria or lead time is InvalidInput, and no default site is InvalidInput naming `defaultSite`. In both cases nothing is stored. Changing the default site, editing the subscribed site or clearing the default moves every affected subscription to `needs_reconfirmation` in the same transaction. Such a subscription schedules nothing until it is enabled again with named values. Basis: PLAN-FR-03, PLAN-FR-06, PLAN-AC-04 and PLAN-AC-06; the repeat identity in D07 includes the target.
- **R13 Permission adapter.** The plugin's desktop permission API always reports Granted and discards delivery errors, so PlateVault never uses it as permission evidence. Core defines a `Notifier` port with states `granted`, `denied`, `not_determined` and `unavailable` with a reason. On macOS the shell adapter uses `UNUserNotificationCenter` for settings, authorization requests and immediate requests with completion results. Only `Authorized` counts as granted. Without a bundle identifier the adapter reads `unavailable` with reason `unbundled_process`. Windows and Linux adapters read `unavailable` with reason `platform_not_qualified` until a platform qualification adds a real adapter. Basis: PLAN-FR-07 and PLAN-AC-08 need a real denial; D07 forbids claiming delivery.
- **R14 Delivery scope.** Reminders are submitted only by the running application. The status and every review report app-closed delivery as unavailable with reason `no_installed_scheduler`. Basis: PLAN-FR-06 and D07. Alternative: queued OS notification triggers could fire while PlateVault is closed. They would fire for windows whose site or criteria changed meanwhile, and no installed, tested scheduler exists.
- **R15 Repeat suppression.** A window identity is Target ID, site ID and the window's UTC start minute. Before submission, the scheduler commits a delivery row in state `sending` under a unique key on that identity. An existing row suppresses the reminder. After submission the row reads `submitted` or `failed` with the reason. At catalog open, a row still `sending` becomes `uncertain` and is never sent again. No state says delivered, because an OS acceptance does not prove the user saw the notice. Basis: D07 durable suppression, PLAN-AC-07, PLAN-FR-07 and J29 S8.
- **R16 Due rule and timing.** A reminder is due from window start minus lead time until window start. After window start it is never sent. The scheduler computes windows for four nights in the site's zone: the night before the current site-local date through two nights after it. It sleeps until the next due instant or for 30 seconds, whichever comes first. It then re-reads the wall clock, which catches up after system sleep, when monotonic timers stall. Basis: resume and restart recompute upcoming windows (D07).
- **R17 Scheduler lifecycle.** The scheduler task exists only while a notifier is attached and at least one subscription is `enabled`. Enabling the first subscription starts it, disabling the last stops it, and catalog open starts it only for persisted enabled subscriptions. Before each submission it reads permission again. A permission that is not granted at that moment moves the subscription to `blocked` with the reason and submits nothing. The scheduler holds only planning catalog operations and the notifier, so it cannot start a scan or image work. Basis: PLAN-AC-05 and PLAN-FR-03.
- **R18 Denial and recovery.** Activation with a denied or unavailable permission commits the subscription as `blocked` with the reason, so the denial stays visible after reload. A `not_determined` permission is requested first. Retry calls activation again with the shown values. Settings opens the platform notification settings through the opener plugin's Rust API. Basis: PLAN-FR-07, PLAN-AC-08 and J29 S6 and S7.
- **R19 Reminder text.** Each notification names the Target, the site, the local start and end with the zone name and the lead time. Basis: PLAN-FR-03 requires every reminder to name its site.
- **R20 Calendar snapshot.** Export review recomputes the windows, requires every selected window key to exist, and returns the site, zone, night range, selected windows and a snapshot digest. Export repeats the request with that digest. It refuses with Conflict when recomputation differs, then opens the native save dialog through `tauri-plugin-dialog`. Canceling the dialog writes nothing. The snapshot is not stored, because the file is the snapshot. Basis: PLAN-FR-04, PLAN-AC-03 and D19, which says calendar export consumes no recorded file.
- **R21 Calendar encoding.** A hand-written RFC 5545 renderer emits CRLF lines folded at 75 octets with escaped text. Each window is a `VEVENT` with UTC `DTSTART` and `DTEND`, a UID derived from the window identity, `LOCATION` with the site name, `GEO` with its coordinates, and a description that names the zone, the local times with offsets and the criteria. The calendar carries `X-WR-TIMEZONE` with the zone name. Basis: UTC instants need no `VTIMEZONE` and stay exact in every client. Alternative: `TZID` with generated `VTIMEZONE` rules adds transition encoding that could disagree with the bundled database.
- **R22 Atomic write.** The snapshot is written to a new temporary file in the chosen directory, synced, renamed onto the chosen path, and the directory is synced. A failure removes the temporary file and leaves any existing file unchanged. A path without the `.ics` extension is refused. Basis: failed writes stay visible and never report saved success (root FR-012).
- **R23 Project gaps.** The Target overview lists the Projects framing the Target through the 065 `project_list` query, and the checklist items that 065 reports unmet or unknown through `project_detail`. It shows them beside the 064 Target coverage. Planning computes no progress itself. Basis: PLAN-FR-02 and 065 contract extensions.
- **R24 Astronomical only.** Window, review and export types carry no weather, equipment, availability or readiness field. No planning path opens a network connection or asks for a provider account. Basis: PLAN-FR-05 and D18.
- **R25 Native surfaces in verification.** MCP drives the IPC and the webview. The native save panel and the OS permission prompt are outside the webview, so host desktop automation answers them while MCP observes the commands and the resulting state. No dev-only path override replaces the native dialog, because PLAN-FR-04 requires it. Basis: D17 makes MCP the mandatory means, and native evidence complements it.
- **R26 Bundled development build.** macOS authorization needs a bundle identifier, and the library shell builds unbundled with `test = true`. The notifier proof therefore runs from a debug application bundle of the library shell with `dev-tools`. Producing it is a qualification task. If no such bundle can carry the dev bridge, PLAN-AC-07 and PLAN-AC-08 runtime proof stays an explicit gap after five attempts, and enabling reports `unbundled_process`. Basis: J29 G2.
- **R27 Naming.** Commands use the `planning_` prefix in `commands/observing_plans.rs`, because legacy commands use plan for filesystem plans.

## Cross-spec seams

- **PRJ (065) progress.** Planning needs `Catalog::list_projects` filtered by Target and `Library::project_detail` with checklist items that carry `met` or evidence states (`specs/065-project-goals/contracts/modules.md:15-24`, `:46`). Conservative default: 072 integrates after 065 and copies those items without recomputing them. If 065 changes the shape, the overview follows the 065 contract.
- **PRJ (065) capture-site names.** The 065 contract says PLAN shows saved-site names beside capture sites. Matching header coordinates to a saved site needs a tolerance that neither spec nor D01 through D19 sets, and 065 R14 applies none. Conservative default: 072 exposes `Catalog::list_sites` and `planning_list_sites`, and capture sites keep showing their coordinates without a name.
- **Siblings 066 to 071.** Their planned schema changes may land before 072. The integration owner assigns the version on the actual base (R1). 072 reads no sibling table.
- **LIB (064) Settings.** 064 owns Settings navigation. 072 supplies the site and default-site commands that the Settings sites section consumes in the final frontend.
- **Library composition.** `Library::open` keeps its signature. The shell attaches the notifier through `Library::attach_notifier`, following `register_references`. The 065 integration also edits `library.rs`, so 072 integrates after it.

## Open questions

- J20 S6 expects capture sites to read Backyard and the second site. That needs a site-matching tolerance, which belongs to a PRJ decision.
- Whether a debug application bundle of the library shell can carry the dev bridge and real macOS authorization (R26, J29 G2).
- Windows and Linux notification adapters need their own permission and submission qualification before reminders can run there.

## Qualification

Generated FITS/XISF fixtures from the 065 guide supply sessions captured at Backyard and the second site. The astroplan reference covers the nights listed in R9. Scheduler tests use a controlled clock and a recording notifier for due, suppression and restart rules. Only the real macOS adapter proves permission and submission. Every scenario compares source hashes before and after. Real development-MCP evidence remains an acceptance gate. No legacy test result proves the rebuild.
