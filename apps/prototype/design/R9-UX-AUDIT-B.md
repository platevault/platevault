### 8b. Inconsistent semantics

1. **"Mark Done" means two things.** In Wrap up's Clean up step it records the step as done and moves nothing (`wrap-up.tsx:231-235`). In Wrap up's Done step it closes the Project (`wrap-up.tsx:495-498`). Both use `wrapup_mark_done`; one has no icon (`:232`), the other a `CheckCheck` icon (`:496`).
2. **"Done" means five things:** run step 6 (`stepName(done)`), Project stage (`status_done`), Wrap up step 4 (`status_done`), a step-state pill (`status_done`), and the Project state. "Complete" is the run action, it lives on the "Done" step, and that step's Box is titled "Completion" (`run_completion`).
3. **"Next" is four different things:** a toolbar action (`shell_next`), a StepBar badge (`run_step_next`), a Wrap up state pill (`projects_col_next`), and the Projects-list column header.
4. **Skip exists only in Wrap up.** Run steps cannot be skipped, but every step is reachable by link, so the user skips implicitly (Prepare → Results, then Results shows Prepare as Next: `derive.ts:1040-1089`). Calibrate's nearest equivalent, "Process without {kind}…", demands a reason (`actions.ts:158-176`).
5. **Undo works for Skip but not for Done** (`wrap-up.tsx:166-181`). Trash Undo resets *all* skipped offers at once (`:296-299,325-328`).
6. **Order is not enforced in Wrap up.** `editable` ignores `current` (`wrap-up.tsx:110`), so Archive can run before Trash, and Mark Done works with every step "To do" (`store/actions/projects.ts:239-246`). The only thing that tracks order is the variant (S1).
7. **Cleanup happens in three places with three UIs:** checkboxes in the Complete dialog, on by default (`done-step.tsx:59-60`); the Done step's selectable Clean up table (`done-step.tsx:231-305`); Wrap up's "Clean up all…" over a non-selectable list (`wrap-up.tsx:214-258`). "Clean" in Wrap up excludes rejects, intermediates and duplicates.
8. **Settling is recorded at different times.** Wrap up Clean up and Archive settle when the operation *starts* (`wrap-up.tsx:201,422`). Trash settles after each approval or skip (`:91-99,285-295`). A run's Complete records state before its cleanup ops run (`done-step.tsx:124-129`).
9. **The primary action has no fixed home.** Select uses a footer, Review a status line, Calibrate a row menu, Prepare a Box header, Results a table row, Done the body Box header, and lifecycle actions the page header. Wrap up uses per-Box headers, with toolbar Next suppressed.

### 8c. Proposed single flow contract (for the user to decide; not adopted)

- **`StepFooter` (shared, components/app):** a fixed bar at the bottom of the step pane, the same for run steps, run group steps and Wrap up steps. Left: the step's state ("2 unresolved"). Right: `[Skip step]` (ghost) and `[Proceed]` (default). Proceed saves any draft, records the step and opens the next one. While a gate is unmet it is disabled with a `Refusal` popover: "Proceed blocked · 2 unresolved ▸". The toolbar Next becomes a shortcut to the same Proceed, and the StepBar "Next" badge is removed.
- **Step operations** (Prepare, Accept/Reject, Assign, Clean up, Trash, Archive) are always `outline` buttons in the toolbar of the table they act on. They are never `default`.
- **Lifecycle** actions (Rename…, Reopen, Move to Trash…) live in a header `DropdownMenu` (`Run ▾` / `Project ▾`). Finishing a run is the Proceed of its last step: "Finish run…".
- **Wrap up = selection, then Proceed**, as the user suggested. Each step shows one `DataTable` with checkboxes, recommended rows pre-selected and rows expandable to file level: Prepared entries per run → Unusable + Project-rejected frames, intermediates, duplicates → Archive moves (from → to) with a destination `Select`. Proceed runs the selected moves through one `ConfirmDialog` with a file table, then advances. Proceeding with nothing selected is the same as Skip. The last step's Proceed is "Close project".
- **Naming:** run step "Done" → "Finish"; Project "Mark Done" → "Close project"; Project stage "Done" → "Closed"; drop "Completion" and "After Complete".

### Proceed / Next / Skip / Complete / Reopen summary

- **Proceed:** no such control in run or group surfaces. Stepbar only links to stages; Next is a badge. Direct navigation permits entering gated Results before Prepare; the derived marker continues to point at unresolved Prepare (`derive.ts:1039-1088`).
- **Skip:** no literal Skip control in run surfaces. Calibration offers “Process without…” but currently requires a reason; it is an exception assignment, not stage skip (`calibrate-step.tsx:257-260,365-398`).
- **Complete:** can complete with earlier gates open; dialog enumerates open stages but also defaults view/intermediate cleanup choices on (`done-step.tsx:53-132`). Group Complete all has no comparable preview.
- **Reopen:** returns to `stageBeforeComplete`, but control changes from header outline/sm to Done-body outline/xs (`runs.ts:324-341`, `run.tsx:160-169`, `done-step.tsx:194-210`).
- **Results “Accept”:** is a result-record acceptance tied to current bytes, not stage progression; there is no Reject, so results acceptance is currently one-sided (`actions.ts:616-638`, `results-step.tsx:181-193`).
- **Action placement:** Select sticky footer; Calibrate section headers/row menus; Prepare a unique header-in-Box action; Results section headers and rows; Done body boxes. Header lifecycle actions move/resize across lifecycle states. Group repeats stage actions inside differently positioned boxes. This is the largest shared-shell consistency issue.
