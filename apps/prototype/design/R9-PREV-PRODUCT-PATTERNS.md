## B. Platform guidance (cited)

**Button hierarchy**
- Apple HIG, Buttons: use a prominent style for the most likely action and "keep the number of prominent buttons to one or two per view". Use style, not size, to mark the preferred choice. The primary role uses the accent colour, destructive uses system red, and you should not "assign the primary role to a button that performs a destructive action". https://developer.apple.com/design/human-interface-guidelines/buttons
- Fluent 2, Button usage: "Only use one primary button in a layout for the most important action". When many minor actions are present, use outline/subtle/transparent on all of them. Do not give secondary actions the same visual weight. https://fluent2.microsoft.design/components/web/react/core/button/usage
- Windows, Buttons: "Expose only one or two buttons to the user at a time". Use concise verb labels. Put commit buttons in the order "Do it" / "Don't do it" / Cancel. https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/buttons

**Menus**
- Apple HIG, Menus: use verb labels and title-style capitalisation. Dim unavailable items (in regular menus). Append "…" when more input follows. Put frequent items first and group items with separators. https://developer.apple.com/design/human-interface-guidelines/menus
- Apple HIG, Context menus: keep them short and relevant. "Support context menus consistently throughout your app". "Always make context menu items available in the main interface, too". Use at most one submenu level. Hide unavailable items. Put destructive items at the end. https://developer.apple.com/design/human-interface-guidelines/context-menus
- Apple HIG, Pull-down buttons: a More (⋯) button suits items that don't need prominent placement, but it can hinder discoverability. List at least about three items. Do not hide a view's primary actions in it. Mark destructive items and confirm them. https://developer.apple.com/design/human-interface-guidelines/pull-down-buttons
- Windows, Menus and context menus: menus and context menus "organize commands and save space by hiding those commands until the user needs them". Commands used frequently get their own button. A context menu holds secondary commands for one element. https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/menus-and-context-menus

**Destructive confirmations**
- Apple HIG, Alerts: no alerts "for common, undoable actions, even when they're destructive"; do alert for an "uncommon destructive action that they can't undo". Titles should be specific (not "Error"). Use specific verb buttons, not OK. Cancel is always titled "Cancel" and is never the default. Default button on the trailing side. https://developer.apple.com/design/human-interface-guidelines/alerts
- Windows, Confirmations (UX guide): "Unnecessary confirmations are annoying". Confirm only significant or unintended consequences. Prefer undo, prevention, and feedback. Use "permanently" for irreversible actions. Do not repeat the main instruction in slightly different words. https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-confirm
- Windows, Dialog controls: always include a safe Close/Cancel. Use specific button text. The "do it" buttons go on the left and the safe action on the right (Windows order, which is the reverse of macOS). https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/dialogs-and-flyouts/dialogs

**Inline errors and status**
- Windows, Dialog controls: "Don't use dialogs for errors that are contextual to a specific place on the page… use the app's canvas itself to show inline errors." (same URL as above)
- Windows, Error messages (UX guide): a good message names the problem, the cause and a solution, and is relevant, actionable, brief, specific and courteous. Use in-place errors for contextual input problems, put them next to the problem, and use the lightest presentation that works. https://learn.microsoft.com/en-us/windows/win32/uxguide/mess-error
- Windows, InfoBar: an inline, non-intrusive notification for app-wide status, with severity levels and an optional action button. Not for confirming user actions. https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/infobar
- Apple HIG, Feedback: integrate status near the items it describes. Reserve alerts for critical, actionable information. https://developer.apple.com/design/human-interface-guidelines/feedback
- Apple HIG, Entering data: validate fields dynamically and give feedback as soon as you detect a problem. https://developer.apple.com/design/human-interface-guidelines/entering-data

**Tooltips, onboarding, appearance, density**
- Apple HIG, Offering help: a tooltip briefly describes the control, in 60 to 75 characters at most. "If you need a lot of text to describe a control, consider simplifying your interface design." https://developer.apple.com/design/human-interface-guidelines/offering-help
- Apple HIG, Onboarding: onboarding should be "fast, fun, and optional". Prefer context-specific tips. Let the user skip a tutorial, but keep it findable in settings. https://developer.apple.com/design/human-interface-guidelines/onboarding
- Apple HIG, Dark Mode: "Avoid offering an app-specific appearance setting". The app should follow the system. https://developer.apple.com/design/human-interface-guidelines/dark-mode . Windows defaults to the user's system theme, and an app may override it: https://learn.microsoft.com/en-us/windows/apps/develop/ui/theming . Make **Match system the default** of the mode control.
- Windows, Compact sizing: compact density is recommended for productivity and data-entry apps (tables, forms, settings), and is applied app-wide as a resource dictionary across all controls, not per surface. https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/compact-sizing
