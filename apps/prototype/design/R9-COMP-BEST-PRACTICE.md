# R9: building the UI as a composition system (cited best practices)

Scope: external best practice only, for the PlateVault v5 prototype rebuild. Repo findings are not repeated here. The prototype inventory is in `design/R9-UX-AUDIT-C.md` §1 (shared components and feature-local duplicates). Platform rules for buttons, menus, confirmations, errors, tooltips and density are in `design/R9-PREV-PRODUCT-PATTERNS.md` §B. Rows below either add to those or are restated briefly where the topic asks for them.
Accessed 2026-10-12. Apple HIG text was read from the HIG JSON data endpoint (`developer.apple.com/tutorials/data/design/human-interface-guidelines/<page>.json`), which holds the same content as the linked HTML page. "App" in the third column means the dense desktop data app: session and frame tables, staged runs, settings.

Target layering that the rows below support ([INFERENCE] synthesis):

| Layer | Owns | Prototype home | Rule |
|---|---|---|---|
| L0 headless | behaviour, a11y, state | Base UI, TanStack Table | never styled in features |
| L1 styled primitives | tokens → look; Button, DropdownMenu, Dialog, Popover, Tooltip | `src/components/ui` | the only place that styles L0 |
| L2 product components | domain-neutral composites: DataTable, PageHeader, Toolbar, RowMenu, BatchBar, StepStrip, EmptyState | `src/components/app` | compose L1 only; slot APIs |
| L3 templates (page shells) | layout + slots: ListPage, DetailPage, SettingsPage, WizardPage | `src/components/app` (new) | one shell per page kind |
| L4 pages | data + copy only | `src/features/*` | no styling, no raw `<button>`, no local look-alikes |

## 1. Atomic Design and its critiques; templates as page shells

| Claim | Source | How it applies |
|---|---|---|
| "Templates are page-level objects that place components into a layout and articulate the design's underlying content structure." | https://atomicdesign.bradfrost.com/chapter-2/ (book, 2016) | Model each page kind (sessions list, run detail, settings pane, wizard) as one template component with named regions, not as per-page layout code. |
| Templates "focus on the page's underlying content structure rather than the page's final content". The skeleton gives "guardrails for the types of content that populate certain design patterns". | same, ch. 2 | The template fixes header, toolbar, table and detail regions. Pages only fill slots, so the header and table position cannot drift per page. |
| Pages "apply real content to templates and articulate variations to demonstrate the final UI and test the resilience of the design system". | same, ch. 2 | Exercise each template with the worst real data (long target names, 10k frames, empty library) before more pages are built on it. |
| "Atomic design is not a linear process, but rather a mental model". Do not read the stages as Step 1 atoms … Step 5 pages. | same, ch. 2 | Pull missing primitives out of real pages as they are found. Do not finish a full atom set first. |
| "Atomic design has nothing to do with web-specific subjects like CSS or JavaScript architecture." | same, ch. 2 | The atoms/molecules/organisms names need not become folder names. Name layers by responsibility (ui / app / templates / features). [INFERENCE] |
| "We're not designing pages, we're designing systems of components" (Stephen Hay, quoted). Chapter title: "Create design systems, not pages". | https://atomicdesign.bradfrost.com/chapter-1/ | Directly states the user's goal: no page-local components. |
| Critique: it is "important … to settle on a vocabulary that makes sense for the team". Frost defends the hierarchy built into the terms but grants the naming problem. (05 Mar 2015) | https://bradfrost.com/links/post/where-atomic-design-fell-short | Use one glossary for component tiers in the rebuild plan. Do not argue taxonomy. |
| Critique: deciding whether a component is a molecule or an organism is a recurring challenge. Frost: molecules are "simple", organisms "relatively complex". (30 Nov 2015) | https://bradfrost.com/links/post/making-sense-of-atomic-design-molecules-and-organisms | A complexity-based taxonomy is fuzzy. Classify by dependency instead: L2 may import L1, never L4. That rule can be enforced by lint (§9). [INFERENCE] |
| Component Driven: build "from the 'bottom up' starting with basic components then progressively combined to assemble screens". Anti-pattern: "Page-based … Not much effort is made to reuse common elements across pages." | https://www.componentdriven.org/ | Names the failure mode audit C §1c found (feature-local look-alikes). |

## 2. Compound components and slot APIs; composition vs configuration

| Claim | Source | How it applies |
|---|---|---|
| Compound components are "two or more components that work together"; "the objective is to provide a more expressive and flexible API", like `<select>`/`<option>` versus `<select options="key1:value1;…">` ("yuck"). (Feb 2019) | https://kentcdodds.com/blog/compound-components-with-react-hooks | `PageHeader`, `Toolbar`, `DataTable` and `RowMenu` take children parts (`PageHeader.Title`, `PageHeader.Actions`) instead of label/handler props. |
| "Implicit state": the parent shares state with its children through context, so the consumer never wires it. | same | `DataTable` shares selection with `BatchBar` and `RowMenu`, so pages cannot desync "N selected" from the batch actions. |
| Every new option or prop adds "implementation complexity" and "API complexity" ("It's *never* 'just an `if` statement'"), and combinations nobody uses still must not break. Kent pushed back on a `closeOnSelection` prop to avoid the "apropcalypse". (2019) | https://kentcdodds.com/blog/inversion-of-control | Against prop explosion. Do not add `showSettingsButton`, `compact` or `variant="calibration"` to shared components. Let pages compose parts. |
| Counterweight: "adding inversion of control for a single use case would just make the code more complicated". Apply AHA and "avoid hasty abstractions". | same | Add slots only where at least two real pages diverge. Otherwise keep a fixed layout. |
| Radix `asChild`: "Radix will not render a default DOM element, instead cloning the part's child and passing it the props and behavior required". The child "must spread props". `asChild` nests (Tooltip.Trigger > Dialog.Trigger > MyButton). | https://www.radix-ui.com/primitives/docs/guides/composition | Shape of trigger composition: behaviour from the primitive, look from the one Button. |
| Base UI: "Use the `render` prop to compose a Base UI part with your own React components", e.g. `<Menu.Trigger render={<MyButton size="md" />}>`. Render props "can be nested as deeply as necessary". | https://base-ui.com/react/handbook/composition | The prototype's primitives are Base UI. Every menu, popover and dialog trigger renders the standard `Button`. That is how "standard buttons for every action" holds even inside menus. |
| Base UI: "Each Base UI component renders the most appropriate element by default … rendering a different element is recommended only on a case-by-case basis". A render function exposes `(props, state)`. | same | Overriding the element is an exception. Lint can flag `render={<button` or `render={<div` in features (§9). [INFERENCE] |
| React Aria: components are "broken down into individual parts with built-in states, render props, and slots", e.g. `<Button slot="previous">`. "Use the exported contexts … to build your own custom patterns", or "drop down to the low-level Hook-based API". | https://react-spectrum.adobe.com/react-aria/components.html | Gives three escape levels (parts → context → hooks), so new L2 components are built without forking L1. |

## 3. Headless + styled layering

| Claim | Source | How it applies |
|---|---|---|
| Radix Primitives is "a low-level UI component library with a focus on accessibility, customization and developer experience … the base layer of your design system". Components "ship without styles". | https://www.radix-ui.com/primitives/docs/overview/introduction | L0 is only behaviour and a11y. Features never import it directly (§9 rule). |
| Base UI is unstyled. "shadcn/ui … uses Base UI as its unstyled foundation." | https://base-ui.com/react/overview/quick-start | Confirms the prototype stack: Base UI (L0) → shadcn-style `components/ui` (L1). |
| shadcn: "This is not a component library. It is how you build your component library." "Open Code: The top layer of your component code is open for modification." | https://ui.shadcn.com/docs | `components/ui` is owned code. Fix a primitive there instead of wrapping it per feature. |
| shadcn Composition: "Every component … shares a common, composable interface. If a component does not exist, we bring it in, make it composable, and adjust its style to match … the rest of the design system." | same | This is the intake rule for a missing component (e.g. a stepper or segmented control): add it to L1/L2 in house style, never page-local. |
| Headless UI provides "the logic, state, processing and API … but do not provide markup, styles, or pre-built implementations". Component libraries "need to support a massive (and seemingly endless) API surface around markup and style customization". | https://tanstack.com/table/v8/docs/introduction | Sessions and frames tables: TanStack for sorting, selection and virtualisation state, with one styled `DataTable` (L2) on top. |
| Headless pros: "Full control over markup and styles". Cons: "More setup", "No markup, styles or themes provided". Choose it if you want "full control over the design". | same | The setup cost is paid once, in `DataTable`. Pages must not use TanStack directly. [INFERENCE] |
| Fluent v9 ships both layers: `Table` primitives plus a `useTableFeatures` hook "designed with feature composition in mind" (`useTableSort`, `useTableSelection`), and an opinionated `DataGrid`. If the scenario "varies a lot from the documented examples please use the `Table` components". | https://raw.githubusercontent.com/microsoft/fluentui/master/packages/react-components/react-table/library/README.md | A mature precedent for "opinionated L2 table + headless escape hatch", which is the DataTable contract to adopt. |

## 4. Design tokens

| Claim | Source | How it applies |
|---|---|---|
| DTCG Format Module 2025.10 is a "Final Community Group Report", 28 October 2025, not a W3C Standard. Tokens are "a methodology for expressing design decisions in a platform-agnostic way". | https://www.designtokens.org/TR/2025.10/format/ | Use it as the token file format for the source of truth. It is portable to Flutter, SwiftUI and WinUI (§10). |
| A token is an object with `$value`. `$type` is set on the token or inherited from the nearest parent group. Aliases are written `{group.token}` and resolve to the target's `$value`. Types include `color`, `dimension` (`px`/`rem`), `duration`, `typography`, `shadow`. | same (§5–8; preview draft https://www.designtokens.org/tr/drafts/format/ dated 08 Sep 2026) | Aliases give the tiers: `{color.palette.slate.900}` → `{color.text.primary}` → `{table.header.text}`. |
| Groups are "arbitrary". Tools "*MUST NOT* try to infer any special meaning or typing of tokens based on a group". | same §9.2 | Put tier meaning in token names and `$type`, not in folder or group names. |
| Material 3 has "three classes of tokens: reference, system, and component". Reference = "all available tokens with associated values". System = "decisions and roles … This is where theming occurs". Component = "design properties assigned to elements in a component". "Each token is named for how or where it's used." | https://m3.material.io/foundations/design-tokens/overview (read via mirror https://github.com/Glavo/md3-reference-hub/blob/main/docs/foundations/design-tokens/overview.md) | Map as ref = palette and raw scale. sys = surface, text, accent, danger, space-N, control-h. comp = table-row-h, toolbar-h, batchbar-h. Themes (warm/cool, light/dark) swap only sys. |
| Material Web: "Each component token maps to a system token, which has a concrete reference value". On the web the tokens are CSS custom properties `--md-ref-*` and `--md-sys-*`. | https://github.com/material-components/material-web/blob/main/docs/theming/README.md | Same shape as the prototype's CSS variables. Features use only sys or comp variables, never ref or raw hex. |
| M3 density scale: "numbered, starting at 0 … negative numbers (-1, -2, -3) as space decreases". "Typically applied by decreasing the top and bottom padding or overall height by 4dp." High density suits "a data table". Do not densify menus, snackbars or dialogs. "Density shouldn't automatically change across breakpoints." | https://m3.material.io/foundations/layout/grids-spacing/density (mirror snapshot lastmod 2026-05-15: https://github.com/Glavo/md3-reference-hub/blob/main/docs/foundations/layout/grids-spacing/density.md) | Make density one sys token that scales `control-h-*` and `space-*` app-wide. Previous product did this, and the current prototype only sets `--row-h` (R9-PREV-PRODUCT-PATTERNS A12). Exclude menus and dialogs. |
| Carbon row sizes: xs 24, sm 32, md 40, lg 48, xl 64 px. Toolbar, batch bar and pagination heights "should always match the row height". | https://carbondesignsystem.com/components/data-table/style/ | comp tokens `toolbar-h`, `batchbar-h` and `pager-h` alias `table-row-h`, which aliases the density sys token. |

## 5. Platform HIG guidance

| Claim | Source | How it applies |
|---|---|---|
| macOS/Apple alerts: "Always place the default button on the trailing side of a row … Cancel buttons are typically on the leading side". Never make Cancel the default. Always title it "Cancel". (HIG change 2024-02-02: "Enhanced guidance for using default and Cancel buttons") | https://developer.apple.com/design/human-interface-guidelines/alerts | Dialog footer order on macOS: [Cancel] [Primary]. |
| Windows ContentDialog: "The 'do it' action button(s) should appear as the leftmost buttons. The safe, nondestructive action should appear as the rightmost button." A safe Close/Cancel is required. | https://learn.microsoft.com/en-us/windows/apps/design/controls/dialogs-and-flyouts/dialogs | The Windows order is the reverse of macOS. |
| GNOME: "Always ensure that the cancel button appears first, before the affirmative button. In left-to-right locales, this is on the left." Do not bind Return to an "irreversible, destructive" affirmative button. Label it "with a specific imperative verb". | https://developer.gnome.org/hig/patterns/feedback/dialogs.html | GNOME matches macOS. [INFERENCE] One `DialogFooter` (L2) owns the order and platform switch, so pages never order buttons themselves. The user is on macOS, so [Cancel][Verb] is the default. |
| Undo vs confirm. Apple: "Avoid displaying alerts for common, undoable actions, even when they're destructive." GNOME: "undo is typically a better option than a confirmation dialog". NN/g: confirm only "actions with serious consequences", not "routine actions". Be specific, e.g. "Delete file" / "Keep file". (NN/g 18 Feb 2018, reviewed 07 Aug 2026) | Apple URL above; GNOME URL above; https://www.nngroup.com/articles/confirmation-dialog/ | Dismissing a master, moving to Trash or removing from a run: undo toast, no dialog. Permanent delete of files on disk: a specific confirm naming the count and paths. |
| Toolbars: "Only specify one primary action, and put it on the trailing side of the toolbar". Use a More menu for less important actions, but "only add this menu if you really need it". The toolbar "can't be the only place that presents a command". Window titles: under 15 characters. | https://developer.apple.com/design/human-interface-guidelines/toolbars | PageHeader/Toolbar contract: title leading, one primary trailing, overflow ⋯ last. Commands also exist in a menu (row or context). |
| Sidebars: "show no more than two levels of hierarchy". Let people hide the sidebar. "Avoid putting critical information or actions at the bottom of a sidebar." | https://developer.apple.com/design/human-interface-guidelines/sidebars | Source list is navigation only (matches FEEDBACK-R1 "Navigation only"). No action buttons pinned at the sidebar's bottom. |
| Context menus: "Always make context menu items available in the main interface, too". Items present in some places but not others make people "think there's a problem". "Consider using a context menu instead of a panel or inspector window to present frequently used functionality." | https://developer.apple.com/design/human-interface-guidelines/context-menus | Supports the user's preference for menus over side fold-outs. Row ⋯ menu and right-click menu come from one action list per row type. |
| Windows: use a menu when the host "is a button … whose primary role is to present additional commands", and a context menu on content. "If a particular command will be used frequently … placing it directly in its own element". | https://learn.microsoft.com/en-us/windows/apps/design/controls/menus-and-context-menus | Named dropdown buttons ("Add ▾", "Export ▾") for command groups. The 1–2 frequent actions stay as visible buttons. |
| Popovers: "expose a small amount of information or functionality". "Never show a cascade or hierarchy of popovers". "Avoid using a popover to show a warning." "Always save work when automatically closing a nonmodal popover." A sheet is for "a scoped task". | https://developer.apple.com/design/human-interface-guidelines/popovers | "Used by N runs" belongs in a popover (FEEDBACK-R1). Editing a master's fields is a sheet or detail view. Never a popover inside a popover. |
| Progressive disclosure: "defers advanced or rarely used features to a secondary screen". "Designs that go beyond 2 disclosure levels typically have low usability." Label the advance control to set "clear expectations". (NN/g, 03 Dec 2006). Apple: "Use a disclosure control to hide details until they're relevant." | https://www.nngroup.com/articles/progressive-disclosure/ ; https://developer.apple.com/design/human-interface-guidelines/disclosure-controls | Settings: basics inline, "Advanced" disclosure as level 2, never level 3. |
| Tooltips. Apple: "Describe only the control"; "avoid repeating a control's name"; "60 to 75 characters"; "If you need a lot of text … consider simplifying your interface design". Windows: "sparingly, and only when they are adding distinct value"; icon-only "command buttons … need tooltips"; "Don't use a tooltip to display text already visible" (2025-02-26). NN/g: "If you can't think of particularly helpful content, don't offer a tooltip"; never hide essential info (27 Jan 2019). | https://developer.apple.com/design/human-interface-guidelines/offering-help ; https://learn.microsoft.com/en-us/windows/apps/design/controls/tooltips ; https://www.nngroup.com/articles/tooltip-guidelines/ | Tooltip rule for the `Tooltip`/`HelpTip` primitive: required on icon-only buttons, forbidden when it repeats a visible label, and essential rules go inline. |

## 6. Data-table patterns from mature systems

| Claim | Source | How it applies |
|---|---|---|
| Carbon toolbar "is reserved for global table actions such as table settings, complex filters, exporting". "Include up to five actions … More actions can be made available through an overflow menu." | https://carbondesignsystem.com/components/data-table/usage/ | Sessions and frames toolbar: search, filters, density/columns, ≤5 actions, then ⋯. |
| Carbon batch actions: once a row is selected "the batch action bar appears at the top of the table". "When batch mode is active, single action icons and overflow menus on the row should be disabled." Exit with cancel "on the far right" or by deselecting all. | same | One `BatchBar` (L2) replaces the toolbar while a selection exists. It is the single flow for multi-row work (add to run, move, trash). |
| Carbon row actions: "Each row is accompanied by an overflow menu". "When the overflow menu contains fewer than three options, keep the actions inline as icon buttons". `overflowMenuOnHover` shows it on hover/focus only, but stays persistent on touch. | same | RowMenu rule: ≥3 actions → ⋯ menu (hover-reveal allowed). 1–2 → inline icon buttons with tooltips. |
| Carbon sorting: controls in column headers; three states (unsorted, up, down). "Only the sorted column displays an icon, and unsorted icons are only visible on hover." | same | Matches the previous product's SortHeader (R9-PREV-PRODUCT-PATTERNS A5). Put it once in `DataTable`. |
| Carbon sizes: five row heights, and toolbar and batch bar "should always match the row height". | https://carbondesignsystem.com/components/data-table/style/ | Density token drives all three (§4). |
| Shopify index table: "Use checkboxes for bulk selection, reveal row actions on hover, and include pagination for large data sets". "Confirm destructive bulk actions" with a modal. "Show feedback when bulk actions complete" with a toast. | https://shopify.dev/docs/api/app-home/patterns/compositions/index-table | Bulk flow: select → BatchBar verb → (confirm only if destructive and irreversible) → toast with count ("2 sessions moved"). |
| Shopify page: "Include page actions in the header only if they are relevant to the entire page." "No more than one primary action and 3 secondary actions per page." "Don't include any actions at the bottom of the page." "Include breadcrumbs when the page is part of a flow." | https://shopify.dev/docs/api/app-home/web-components/layout-and-structure/page | Contract for the L3 page shell header (title, breadcrumb slot, 1 primary + ≤3 secondary + ⋯). |
| Atlassian dynamic table: "Never put additional controls like links or buttons in table headings." Make edit labels unique per row ("Edit component 3", not "Edit"). Put edit and delete in the "more actions" menu when there are several actions. | https://atlassian.design/components/dynamic-table/usage | Headers hold only sort. RowMenu items get row-specific accessible names. |
| Fluent: opinionated `DataGrid` built on `Table` + `useTableFeatures`, with "full feature parity with what can be achieved with primitives". | https://raw.githubusercontent.com/microsoft/fluentui/master/packages/react-components/react-table/library/README.md | If a page needs a non-standard table, extend `DataTable` through its parts or hooks. Do not build a second table. |

## 7. Wizard / stepper patterns

| Claim | Source | How it applies |
|---|---|---|
| NN/g: "Use wizards for novice users or infrequent processes (e.g., configuration or setup)." If users repeat the task, "consider offering them another faster alternative". (25 Jun 2017) | https://www.nngroup.com/articles/wizards/ | Use a wizard for setup and New Project. Repeated staged run work should be a page with a step strip, not a modal wizard. [INFERENCE] |
| "Communicate a clear mental model … displaying a list or a diagram of the steps … highlighting the current step." "Enforce a clear sequential order." If any order is useful, a wizard is the wrong tool. | same | One `StepStrip` (L2) shared by the setup wizard and the run stages. |
| "Generic labels such as *Next* and *Previous* have weak information scent". "Indicate in the label what the user will actually have to do next." | same | Prefer "Continue to calibration" over "Next" where space allows. Keep it consistent (Apple row below). |
| "Allow users to exit the wizard midway and save state." Steps should be "self-sufficient". | same | Staged runs persist each step. Cancel never loses completed steps. |
| NN/g staged disclosure is "useful when you can divide a task into distinct steps that have little interaction" and "problematic when the steps are interdependent". (2006) | https://www.nngroup.com/articles/progressive-disclosure/ | Reason to keep run steps inspectable out of order (Review ↔ Calibrate) on the run page, not as a locked wizard. [INFERENCE] |
| Carbon progress indicator: use it for "a linear process … three or more steps". Do not use it when "the process may be completed in any order" or "the number of steps may change". Labels: 1–2 words, "{verb} + {noun}". States: completed, current, not started, error, disabled. Optional steps go in helper text. | https://carbondesignsystem.com/components/progress-indicator/usage/ | StepStrip states and label style. Optional steps (e.g. calibration) show "Optional" helper text, not a separate flow. |
| PatternFly: default footer buttons are "**Back**, **Next**, and **Cancel**"; "Use only 1 primary action in the footer, typically **Next**"; "**Back** is disabled on the first step"; optional "**Skip to finish**"; "Closing discards unsaved edits, so show a confirmation". | https://www.patternfly.org/components/wizard/design-guidelines | Footer semantics for `WizardPage` (L3): Back (ghost), Cancel, primary Next. Skip only on optional steps. |
| PatternFly: "Always end with a review step." On the last step Next becomes Finish. "Replace it with a more specific verb … such as **Create**." Show a progress screen if applying takes seconds. "After submit, hide the steps sidebar." | same | Last step "Create project" / "Start run". Then a progress empty state, then a result. |
| Apple: for multi-step flows "decide how you want to label the actions … 'Continue' or 'Next,' but be consistent". "Make it clear when a flow is complete by using language like 'Done.'" | https://developer.apple.com/design/human-interface-guidelines/writing | One label set for every staged flow in the app. |

## 8. Microcopy

| Claim | Source | How it applies |
|---|---|---|
| GOV.UK: "Write button text in sentence case, describing the action it performs" ("Start now", "Sign in"). | https://design-system.service.gov.uk/components/button/ | Buttons are verb + object, sentence case: "Add to run", "Integrate master". |
| GOV.UK: warning buttons "only work if used very sparingly. Most services should not need one." | same | The destructive variant only for irreversible actions (R9-PREV-PRODUCT-PATTERNS A1 split of danger vs destructive). |
| GOV.UK: "Plain English is mandatory". Words to avoid include deliver, empower, facilitate, key, leverage, robust, streamline, utilise, transform. "Avoid using metaphors". | https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/style-guides/a-to-z-style-guide | A ready-made anti-slop word list. A copy lint over `messages/en-GB.json` can reject these words (§9). [INFERENCE] |
| GOV.UK: "Use the active voice". "Always use sentence case, even in page titles". Content design "starts by taking a user need". You may need to "reduce the amount of content". | same; https://guidance.publishing.service.gov.uk/writing-to-gov-uk-standards/plan-manage-content/understand-content-design/ | Matches the FEEDBACK-R1 copy rule (microcopy only, no explanatory captions). |
| Microsoft: "sentence-style capitalization … Capitalize the first word of a … UI label (such as the name of a button or checkbox)". (2024-08-26) | https://learn.microsoft.com/en-us/style-guide/capitalization | Same rule across menus, headers and buttons. Note that Apple menus use title case (R9-PREV-PRODUCT-PATTERNS §B). Pick one style per element type (Apple row below). |
| Windows: button text is "a couple short words" at most; "use the *active voice*"; "Don't end text for buttons … with a period". Dialog title and buttons are "call and response": "buttons are clear answers to the question posed by the title". (2020-09-24) | https://learn.microsoft.com/en-us/windows/apps/design/style/writing-style | Dialog: "Delete 12 frames from disk?" → [Cancel] [Delete frames]. |
| Apple: "When labeling buttons and links, it's almost always best to use a verb … just saying 'Send' often works better than 'Let's do it!'". Avoid "we" in errors: "'Unable to load content' is much clearer". "Interjections like 'oops!' … can sound insincere." "Choose a style for each UI element type and use it consistently." | https://developer.apple.com/design/human-interface-guidelines/writing | Anti-slop: no chirpy CTAs, no "we", no "oops". Capitalisation fixed per element type. |
| NN/g errors: display "close to the error's source"; "human-readable language"; "Concisely and precisely describe the issue"; "Offer constructive advice"; don't use "*invalid*, *illegal*, or *incorrect*"; "Preserve the user's input". (14 May 2023) | https://www.nngroup.com/articles/error-message-guidelines/ | Inline field errors in Settings. Refusals name the cause and the fix ("Can't remove rig · used by 3 runs ▸"). |
| Windows errors: an error "doesn't blame the user". Tell "what went wrong", "what will happen next", and give "a realistic solution". | https://learn.microsoft.com/en-us/windows/apps/design/style/writing-style | Failed-work toasts: "Couldn't read 3 files. Retry". |
| Apple tips: "Keep your tips to one or two sentences and avoid including content that's promotional". | https://developer.apple.com/design/human-interface-guidelines/offering-help | Onboarding stops: one sentence, no marketing tone. |

## 9. Enforcement and governance

| Claim | Source | How it applies |
|---|---|---|
| ESLint `no-restricted-syntax` accepts "AST selectors" with a custom `message`. | https://eslint.org/docs/latest/rules/no-restricted-syntax | Ban look-alike markup in `src/features/**`, e.g. selector `JSXOpeningElement[name.name='button']` with message "Use <Button>" (also `table`, `select`, `dialog`), and `JSXAttribute[name.name='style']`. [INFERENCE: selector strings not run against the repo] |
| `react/forbid-elements`: "forbid usage of certain elements in favor of others". Checks JSX and `React.createElement`.
